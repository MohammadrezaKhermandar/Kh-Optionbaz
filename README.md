## هدف محصول

یک میزکار تصمیم‌گیری که به این پرسش‌ها جواب بدهد:

- زنجیره‌ی اختیار و داده‌ی بازار الان چه می‌گوید؟
- کدام فرصت‌ها با توجه به **نقدشوندگی، هزینه‌ی اجرا، سرمایه‌ی لازم و
  ریسک** ارزش نگاه‌کردن دارند؟
- وضعیت بازار چیست (روند صعودی، نزولی، رنج، پرنوسان)؟
- توزیع احتمالی نماد پایه تا سررسید هر قرارداد چگونه است؟
- برای **این معامله‌ی مشخص**: احتمال سود، بازده خالص مورد انتظار، و زیان
  سناریوهای بد چقدر است؟
- اخبار مرتبط (از یک سرویس مستقل و لوکال) چه می‌گویند؟

با شخصی‌سازی بر پایه‌ی سرمایه، دارایی پایه، تحمل زیان و محدودیت‌های کاربر.

سه اصل که کل مسیر توسعه را مقید می‌کنند:

1. **پیش‌بینی جهت**، **احتمال سود معامله** و **امتیاز قدرت سیگنال** سه
   چیز جدا هستند و نباید در یک عدد قاطی شوند.
2. هیچ نرخ برد یا مزیت معاملاتی بدون داده و اعتبارسنجی وعده داده نمی‌شود.
3. هر عددی که نمایش داده می‌شود یا قابل بازسازی است، یا صریحاً
   «نامعلوم» است.

وضعیت فعلی محصول و آنچه هنوز قابل استناد نیست:
[docs/known-limitations.md](docs/known-limitations.md)
مسیر پیشِ رو: [docs/roadmap.md](docs/roadmap.md)

### پیش‌نیاز

- Python **3.11** یا بالاتر
- برای هسته‌ی ربات: فقط `PyYAML`
- برای داشبورد وب: `fastapi` و `uvicorn`
- برای تست: `pytest` و `httpx`

`pandas`، `numpy` و `scipy` در `requirements.txt` هستند ولی مسیرهای
اصلی به آن‌ها نیاز ندارند (قیمت‌گذاری با کتابخانه‌ی استاندارد کار می‌کند).
`pytse-client` هم فقط برای provider جایگزین `pytse` لازم است که مسیر
اصلی نیست.

```powershell
cd option_signal_bot
py -3 -m venv .venv
.\.venv\Scripts\python.exe -m pip install PyYAML fastapi uvicorn pytest httpx
```

### تنظیمات

```powershell
copy config\settings.example.yaml config\settings.yaml
```

`config/settings.yaml` در `.gitignore` است و **هرگز نباید کامیت شود**.

### اجرا با داده‌ی ضبط‌شده (بدون حساب)

سریع‌ترین راه برای اطمینان از سالم‌بودن نصب. در `settings.yaml`:

```yaml
option_chain:
  provider: fixture
  fixture_path: tests/fixtures/tsetmc_option_market_watch.json
market_data:
  provider: tsetmc
  fixture_path: tests/fixtures/tsetmc_option_market_watch.json
  history_dir: tests/fixtures/history
  symbols: [خودرو, شستا, اهرم]
trading_calendar:
  learn_from_market: false
general:
  run_only_when_market_open: false
# برای این بررسی هر دو خاموش بمانند
broker:
  enabled: false
notifiers:
  telegram:
    enabled: false
    commands_enabled: false
```

```powershell
.\.venv\Scripts\python.exe main.py --config config\settings.yaml --once
```

این حالت روی پاسخ‌های واقعیِ **ضبط‌شده‌ی** TSETMC اجرا می‌شود. با این
تنظیمات هیچ مسیر داده‌ای به شبکه نیاز ندارد، ولی خودِ برنامه چیزی را
مسدود نمی‌کند: «بدون شبکه بودن» نتیجه‌ی همین پیکربندی است، نه یک گارد
داخلی. اگر به تضمین نیاز دارید، بخش
«[تأیید بدون‌شبکه‌بودن](#تأیید-بدونشبکهبودن-اختیاری)» را ببینید.

### اجرا با داده‌ی زنده

داده از API عمومی TSETMC خوانده می‌شود — **بدون نیاز به لاگین، توکن یا
حساب کارگزاری**.

برای تبدیل تنظیمات آفلاین بالا به زنده، این چهار تغییر لازم است:

1. `option_chain.provider` را از `fixture` به `tsetmc` تغییر دهید.
2. `option_chain.fixture_path` را **حذف کنید**.
3. `market_data.fixture_path` را **حذف کنید** (`provider: tsetmc` بماند).
4. `market_data.history_dir` را **حذف کنید** — تا وقتی باشد، تاریخچه از
   دیسک خوانده می‌شود نه از شبکه.

حذف‌نکردن هرکدام از این سه کلید یعنی همان مسیر از داده‌ی ضبط‌شده تغذیه
می‌شود و اجرا فقط **بخشی** زنده خواهد بود، بدون اینکه خطایی بدهد.

```yaml
option_chain:
  provider: tsetmc
market_data:
  provider: tsetmc
  symbols: [خودرو, شستا, اهرم]
```

```powershell
.\.venv\Scripts\python.exe main.py --config config\settings.yaml --once
```

### ثبت تاریخچه‌ی خام بازار (recorder)

زنجیره‌ی بازار **پیش از** فیلترهای کیفیت ثبت می‌شود: قراردادی که امروز
بی‌مظنه است فردا ممکن است نقدشونده شود، و اگر امروز ثبتش نکنیم آن
تاریخچه برای همیشه رفته. مستقل از حساب کارگزاری، تلگرام و لایه‌ی اجرا.

```powershell
# یک نوبت ثبت زنده
.\.venv\Scripts\python.exe scripts\record_market.py --once

# روی پاسخ ضبط‌شده، در پایگاه آزمایشیِ جدا
.\.venv\Scripts\python.exe scripts\record_market.py --once --kind test `
    --fixture tests\fixtures\tsetmc_option_market_watch.json `
    --db var\recorder\test.db

# وضعیت محلی — هیچ درخواست شبکه‌ای نمی‌زند
.\.venv\Scripts\python.exe scripts\record_market.py --status

# ثبت منظم تا وقتی با Ctrl+C متوقفش کنید
.\.venv\Scripts\python.exe scripts\record_market.py --loop
```

**قفل نویسنده:** هر اجرای نوشتنی — `--once` و `--loop`، هر دو — پیش از
دریافت یک قفل انحصاری روی `<پایگاه>.lock` می‌گیرد. پس دو نویسنده روی
یک پایگاه ممکن نیست: نمونه‌ی دوم بی‌آنکه درخواستی بزند یا فایلی بسازد
با کد ۲ خارج می‌شود. قفل با مرگ پردازه **خودکار** آزاد می‌شود.
`--status` قفل نمی‌گیرد و همیشه قابل استفاده است، حتی وسط یک `--loop`.

### ثبت منظم (`--loop`)

پیش‌فرض: هر **۳۰۰ ثانیه**، از **۰۹:۰۰ تا ۱۲:۳۰** به وقت تهران، به‌علاوه
۵ دقیقه مهلت پس از پایان جلسه. همه از بخش `recorder` تنظیمات قابل
تغییرند؛ `--interval` بر تنظیمات مقدم است.

| رفتار | چگونه |
|---|---|
| **بدون هم‌پوشانی** | نوبت بعدی از **ساعت دیوار** حساب می‌شود، نه از پایان نوبت قبلی. نوبتی که طول بکشد، اسلات بعدی را می‌بلعد |
| **بدون جبران انبوه** | پس از خوابِ ویندوز، اسلات‌های ازدست‌رفته **پرش** می‌شوند (با هشدار در لاگ) و فقط یک نوبت اجرا می‌شود |
| **انتظار ≠ خرابی** | بیرون بازه هیچ دریافتی و **هیچ ردیفی** ثبت نمی‌شود؛ فقط لاگ |
| **خطای موقت** | ثبت می‌شود و حلقه ادامه می‌دهد. لایه‌ی retry تازه‌ای روی retry موجود گذاشته نشده |
| **خطای غیرقابل ادامه** | تنظیمات، قفل، و نسخه‌ی پایگاه **پیش از** ورود به حلقه بررسی می‌شوند |
| **تک‌نمونه** | همان قفل نویسنده‌ی بالا — که `--once` را هم پوشش می‌دهد، نه فقط حلقه را |
| **توقف** | Ctrl+C: قفل آزاد، اتصال بسته، خلاصه‌ی نوبت‌های موفق/ناموفق، خروج ۰ |

⚠️ **تاریخچه‌ی ازدست‌رفته بازسازی نمی‌شود.** اگر ماشین یک روز خاموش
بماند، آن روز رفته است.

⚠️ snapshotهای پس از پایان جلسه **«قیمت پایانی» نیستند** — منبع هیچ مهر
زمانی نمی‌دهد، پس فقط مشاهده‌ی عادی‌اند.

**راه‌اندازی روی ویندوز:** فعلاً یک پنجره‌ی PowerShell با `--loop` باز
بماند. سیستم باید روشن باشد و خواب نرود
(`powercfg /change standby-timeout-ac 0` — با اختیار خودتان). پس از
restart باید دستی دوباره اجرا شود؛ نصب Task Scheduler عمداً در این
مرحله انجام نشده.

کد خروجی: `0` موفق، `1` دریافت/پردازش ناموفق، `2` استفاده‌ی نادرست.

مسیر پایگاه و پیش‌فرض‌ها از بخش `recorder` در `config/settings.yaml`
می‌آیند؛ آرگومان صریح CLI بر آن‌ها مقدم است. `--kind test` بدون `--db`
هم به مسیر آزمایشی می‌رود، پس هیچ‌وقت پایگاه زنده را لمس نمی‌کند.

**وضعیت هر نوبت:** `complete` (بدون مشکل)، `complete_with_issues`
(ثبت شد ولی پاسخ **تعارض**، ردیف استخراج‌نشده یا **فیلد عددی نامعتبر**
داشت) یا `failed`. یک `snapshot_id` که ثبت شده با محتوای متفاوت
بازنویسی نمی‌شود؛ مشاهده‌ی تازه شناسه‌ی تازه می‌گیرد.

**نسخه‌ی اسکیما:** پایگاهی که با نسخه‌ی دیگری از اسکیما نوشته شده،
با خطای روشن رد می‌شود و **دست‌نخورده** می‌ماند. مهاجرت خودکار وجود
ندارد. اگر چنین خطایی دیدید، پایگاه قدیمی را نگه دارید و برای ثبت
تازه یک مسیر دیگر بدهید:

```powershell
# پایگاه قدیمی را کنار بگذارید (پاکش نکنید — داده‌اش سالم است)
Rename-Item var\recorder\market.db market-schema-v2.db

# و از همین‌جا به بعد روی مسیر پیش‌فرض، پایگاه تازه ساخته می‌شود
.\.venv\Scripts\python.exe scripts\record_market.py --once
```

برای خواندن پایگاه قدیمی، همان نسخه‌ی کدی که ساخته‌اش لازم است؛
`sqlite3` هم مستقیم بازش می‌کند.

**داده‌ی آزمایشی و زنده هرگز در یک پایگاه مخلوط نمی‌شوند.** نوع پایگاه
هنگام ساخت مهر می‌شود و لایه‌ی ذخیره‌سازی مستقل از CLI کنترلش می‌کند؛
هیچ فلگی نمی‌تواند دورش بزند.

⚠️ **حلقه‌ی زمان‌بندی هنوز نیست** — هر اجرا یک نوبت. اجرای مداوم با
تناوب ۵ دقیقه در مرحله‌ی بعد.

**حجم:** هر نوبت حدود **۲۱۵ KiB** به پایگاه اضافه می‌کند (اندازه‌گیری‌شده
روی ۸ نوبت متوالی؛ شامل payload فشرده، ردیف‌ها و ایندکس‌ها). با تناوب
۵ دقیقه‌ای ≈ ۱.۹ GiB در سال.

**پشتیبان‌گیری:** کپی ساده‌ی فایل هنگام نوشتن می‌تواند پایگاه نیمه‌نوشته
بدهد. از `MarketRecorder.backup_to(path)` استفاده کنید که API خودِ
SQLite را صدا می‌زند و قفل‌ها را رعایت می‌کند، یا از بیرون
`sqlite3 market.db ".backup out.db"`.

پایگاه در `var/` می‌نشیند که در `.gitignore` است — داده‌ی بازار وارد
Git نمی‌شود.

### تست

```powershell
.\.venv\Scripts\python.exe -m pytest -q
```

این همان چیزی است که CI اجرا می‌کند. تست‌ها روی داده‌ی ضبط‌شده نوشته
شده‌اند و در عمل به ساعت بازار یا توکن نیاز ندارند.

#### گارد شبکه چه چیزی را تضمین می‌کند و چه چیزی را نه

`tests/test_no_network_guard.py` یک fixture به‌نام `no_network` دارد که
سوکت‌های غیرلوکال را می‌شکند. محدودیتش را دقیق بدانید:

- این fixture **انتخابی** است، نه `autouse`. فقط **۷ تست در همان یک
  فایل** از آن استفاده می‌کنند — از مجموع ۹۲۱ تست سوئیت.
- پس گارد می‌گوید «این چند مسیر مشخص (ساخت اپ، تقویم، یک پاس کامل،
  وضعیت داشبورد) آفلاین می‌مانند»، **نه** «هیچ تستی در کل سوئیت به
  شبکه نمی‌رود».
- اجرای معمولی `pytest` و اجرای CI **هیچ مسدودسازی سراسری سوکت
  ندارند**. اینکه بقیه‌ی تست‌ها شبکه نمی‌زنند حاصل استفاده‌شان از
  fixtureهاست، نه حاصل یک قید اجراشده.

#### تأیید بدون‌شبکه‌بودن (اختیاری)

اگر به تضمین سراسری نیاز دارید — مثلاً پیش از اجرا روی ماشینی که نباید
بیرون برود — سوکت را در سطح فرآیند مسدود کنید و بعد pytest یا
`main.py` را اجرا کنید. این کار **بیرون از مخزن** انجام می‌شود و بخشی
از سوئیت یا CI نیست؛ در بررسی مرحله‌ی انتقال از همین روش استفاده شد.

## مرزهای ایمنی

این قیدها در کد اعمال و با تست تضمین شده‌اند و باید حفظ شوند:

| قید | جای اعمال |
|---|---|
| هیچ ماژولی بیرون از `execution/` آن را import نمی‌کند (جز `web/api.py` برای معاملات کاغذی) | گارد AST در `tests/test_signal_generator.py` |
| چند مسیر کلیدی (ساخت اپ، تقویم، یک پاس کامل، وضعیت داشبورد) آفلاین می‌مانند — **نه** کل سوئیت | fixture انتخابی `no_network` در `tests/test_no_network_guard.py` |
| استراتژی به نوتیفایر، دیتابیس یا لایه‌ی اجرا دسترسی ندارد | `StrategyContext` + گارد AST |
| اتصال کارگزاری فقط‌خواندنی است و پیش‌فرض خاموش | `broker.enabled: false` |
| اجرای واقعی سفارش پیاده‌سازی نشده | `execution.enabled: false` |

**هرگز کامیت نکنید:** `config/settings.yaml`، فایل نشست کارگزاری، توکن
تلگرام، فایل HAR، محتویات `var/` یا هر داده‌ی حساب شخصی.
