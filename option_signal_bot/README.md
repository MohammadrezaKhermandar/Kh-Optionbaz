# سیستم سیگنال‌دهی دستی معاملات آپشن بورس تهران
[![CI](https://github.com/OmidRafiee/GarnetTrader/actions/workflows/ci.yml/badge.svg)](https://github.com/OmidRafiee/GarnetTrader/actions/workflows/ci.yml)

ربات بازار آپشن بورس تهران را رصد می‌کند و وقتی شرایط یک استراتژی برقرار شد،
یک **سیگنال معاملاتی** (نه سفارش خودکار) تولید و از طریق تلگرام / لاگ / کنسول نمایش می‌دهد.
کاربر خودش سیگنال را دستی در سامانه معاملاتی‌اش اجرا می‌کند.

> ⚠️ **هیچ اتصالی به API خرید/فروش کارگزاری در این پروژه وجود ندارد.**
> فقط یک اینترفیس انتزاعی خالی (`execution/order_executor_interface.py`) برای آینده گذاشته شده
> که پیاده‌سازی واقعی‌اش را بعداً خود کاربر می‌دهد.

**وضعیت فعلی:** مایل‌استون ۱ کامل + **داده واقعی بازار وصل شد** (TSETMC، بدون لاگین).
**۸۸۲ تست پاس** (تأییدشده، همه روی داده‌ی واقعی). برای اجرا اول بخش «آماده‌سازی محیط» را ببینید.

## داشبورد وب

راه راحت‌تر برای دیدن سیگنال‌ها و تغییر تنظیمات، بدون دست‌زدن به yaml.
دابل‌کلیک روی `8-dashboard.bat`، یا:

```powershell
.\.venv\Scripts\python.exe -m web
```

مرورگر خودکار روی `http://127.0.0.1:8787` باز می‌شود.

| تب | چه کاری می‌کنید |
|---|---|
| **سیگنال‌ها** | سیگنال‌های ثبت‌شده با فیلتر استراتژی و نماد؛ دکمه‌ی اجرای پاس رصد بازار |
| **استراتژی‌ها** | خاموش/روشن کردن هر استراتژی و تغییر پارامترهایش (پیش‌فرض هر پارامتر زیرش نوشته شده) |
| **نمادها** | انتخاب نمادهای پایه از لیست زنده‌ی بازار — فقط نمادهایی که واقعاً آپشن دارند |
| **ریسک** | دارایی حساب، درصد ریسک، سقف قرارداد، حد ضرر و سود |
| **ساختارها** | اسکن استردل/کالر/آیرون کاندور روی زنجیره واقعی + نقشه سفارش |
| **گزارش** | عملکرد سیگنال‌ها با قیمت واقعی، به تفکیک استراتژی و نماد + خروجی CSV |
| **حساب** | پوزیشن‌های واقعی کارگزاری (فقط خواندن) + تنظیم توکن از خود پنل |

تغییرات در `config/settings.yaml` ذخیره می‌شود و **از پاس بعدی** اعمال می‌گردد.

### تمرینِ کلِ مسیر در پنج دقیقه (حالت آزمایشی)

> تصویرِ هر مرحله: [`docs/ui-tour.md`](../docs/ui-tour.md)


تا وقتی recorder چند جلسه‌ی معاملاتی ثبت نکند، سنجه‌ی «تداوم معامله»
نامعلوم می‌ماند و غربال هیچ قراردادی را «قابل معامله» نمی‌کند — پس
فهرستِ فرصت‌های **واقعی** به‌درستی خالی است. برای اینکه بدون انتظار
برای بازار، یک بار کلِ جریان را ببینید، حالت تمرین هست:

```powershell
.\.venv\Scripts\python.exe -m web
```

سپس در مرورگر:

۱. تب **سیگنال‌ها** ← کارتِ «رتبه‌بندی اولویت بررسی» ← دکمه‌ی
   **«حالت تمرین (دادهٔ آزمایشی)»**. (یا مستقیم
   `http://127.0.0.1:8787/?ranking=demo`.)
۲. سه فرصتِ نمونه رتبه می‌گیرند و چهارتای دیگر با **علت** کنار می‌روند —
   اسپردِ مرده، ورودِ اجراناپذیر، فروش، و پایه‌ی ساختارِ چندپایه. کارتِ
   هر فرصت می‌گوید چرا این رتبه را گرفته، ضعفش کجاست و چه چیزی نامعلوم
   مانده.
۳. روی فرصتِ اول، تعداد را بگذارید ۱۰ و **«بررسی با دادهٔ تازه»** را
   بزنید: قیمتِ اجراییِ ورود، وجهِ لازم، حداکثر زیان، سر‌به‌سر و
   امتیازِ **همین لحظه** دوباره حساب می‌شوند.
۴. **«تأیید و ثبت کاغذی»** را بزنید. تأیید فقط تا عمرِ همان بررسی معتبر
   است؛ تعداد را عوض کنید، خودش باطل می‌شود و باید دوباره بررسی کنید.
۵. تب **معاملات کاغذی**: موقعیتِ باز، ارزش روز، سود/زیانِ شناور، و
   کشوی **«تصمیمِ ورود — چرا و با چه اطلاعاتی»** که عکسِ ارزیابیِ لحظه‌ی
   تصمیم را نگه داشته است.
۶. «بستن پوزیشن» را بزنید و در همان تب نتیجه را ببینید.

چند نکته که عمدی‌اند:

* حسابِ تمرین پایگاهِ **جدا** دارد (`var/paper_trading_sandbox.db`)،
  موجودی و نرخ کارمزدِ ثابت و اعلام‌شده، و هیچ‌وقت با حسابِ کاغذیِ
  واقعی قاطی نمی‌شود. ریست هم فقط همان حسابی را پاک می‌کند که در آن
  ایستاده‌اید.
* قیمتی که روی کارت می‌بینید، قیمتی که در بررسی می‌آید و قیمتی که
  سفارش با آن پر می‌شود **یکی** است — از یک دفترِ سفارش.
* در مسیر **واقعی** هم همین جریان است، با این تفاوت که داده از بازار
  می‌آید: اگر فرصتی نباشد، علتش زیرِ هر گزینه نوشته می‌شود و آستانه‌ها
  برای پرشدنِ فهرست پایین نمی‌آیند.

### وضعیت بازار و نماد پایه

کارتِ «وضعیت بازار و نماد پایه» در تب سیگنال‌ها می‌گوید بازار و هر نماد
پایه **تا امروز** چه کرده‌اند: صعودی، نزولی، رنج یا نامشخص — هر کدام
جداگانه، با قدرتِ روند (کاراییِ حرکت)، نوسان، افقِ تحلیل، تازگیِ داده و
دلیلِ حکم.

| سنجه | یعنی چه |
|---|---|
| تغییر قیمت در افق | از ابتدای افق (پیش‌فرض ۲۰ جلسه) تا آخرین جلسه‌ی کامل |
| کارایی حرکت | `تغییر خالص ÷ مجموع حرکت روزانه` — نزدیک ۱ یعنی مسیر مستقیم، نزدیک ۰ یعنی رفت‌وبرگشت |
| نوسان روزانه | انحراف معیار بازده؛ از آن «حرکتِ معمولِ این بازه» ساخته می‌شود |
| تغییر نسبت به نوسان | تغییرِ واقعی ÷ حرکتِ معمول — آستانه‌ی ثابت برای همه‌ی نمادها بی‌معناست |

روی کارتِ هر فرصت هم یک خطِ «تناسب با وضعیت» می‌آید: جهتِ فرصت با
وضعیتِ سهم و بازار می‌خواند یا در تعارض است، و عمرِ باقی‌ماندهٔ قرارداد
در برابر افقِ تحلیل چقدر است.

⚠️ سه قید که عمدی‌اند:

* این **توصیفِ وضعیتِ فعلی** است، نه پیش‌بینی تا سررسید. هیچ درصد
  اطمینان یا احتمال بردی ساخته نمی‌شود.
* در **امتیازِ رتبه‌بندی وارد نمی‌شود** — مؤلفه‌ای که اعتبارسنجی نشده
  نباید بی‌صدا در رتبه بنشیند.
* دادهٔ کم یا کهنه «نامشخص» می‌دهد، نه «رنج».
* **تعدیل قیمت و مرزهایش:** قیمتِ سهم پیش از تحلیل با **افزایش
  سرمایه** تعدیل می‌شود. اگر نشود پرسید، وضعیت «نامعلوم» ثبت می‌شود و
  **حکمِ صعودی/نزولی اصلاً صادر نمی‌شود** — چون افزایش سرمایه‌ی
  تعدیل‌نشده دقیقاً شکلِ یک روندِ قوی را دارد. **سود نقدی در هیچ حالتی
  تعدیل نمی‌شود** (منبع عمومیِ قابل اتکا ندارد)، پس حتی «تعدیل‌شده» هم
  یعنی «افزایش سرمایه اعمال شد»، نه «سری کاملاً هم‌مبنا است».

«بازار» پیش‌فرض شاخص کل بورس تهران است
(`regime.market_ins_code` در تنظیمات).

### ساختارهای چندپایه

| ساختار | پایه‌ها | سود | زیان |
|---|---|---|---|
| **لانگ استردل** | خرید کال + خرید پوت (هم‌استرایک) | نامحدود | محدود به پرمیوم |
| **کالر** | سهم + خرید پوت + فروش کال | سقف‌دار | کف‌دار |
| **آیرون کاندور** | خرید/فروش پوت + فروش/خرید کال | اعتبار خالص | عرض اسپرد − اعتبار |
| **اسپرد صعودی کال** | خرید کال پایین + فروش کال بالا | عرض − هزینه | هزینه |
| **اسپرد نزولی کال** | فروش کال پایین + خرید کال بالا | اعتبار | عرض − اعتبار |
| **اسپرد صعودی پوت** | فروش پوت بالا + خرید پوت پایین | اعتبار | عرض − اعتبار |
| **اسپرد نزولی پوت** | خرید پوت بالا + فروش پوت پایین | عرض − هزینه | هزینه |
| **اسپرد تقویمی** | فروش سررسید نزدیک + خرید دور (هم‌استرایک) | **نامعلوم** ⚠️ | **نامعلوم** ⚠️ |

از تب «ساختارها» روی زنجیره‌ی واقعی اسکن می‌شوند، با مرتب‌سازی بر اساس
ROI، ریسک/ریوارد، نقدشوندگی و ۷ معیار دیگر.

⚠️ **دو نکته که در محاسبات جدی گرفته شده‌اند:**

**۱. سود نامحدود `None` است، نه صفر.** لانگ استردل سود نامحدود دارد؛ اگر
صفر گزارش شود، در مرتب‌سازی ته لیست می‌افتد — برعکس واقعیت.

**۲. اجرای پایه‌ها اتمیک نیست.** در کشف API ایزی‌تریدر هیچ endpoint
سفارش چندپایه پیدا نشد، پس پایه‌ها **جدا** ثبت می‌شوند و بین آن‌ها
قیمت می‌تواند حرکت کند. هر ساختار چندپایه با برچسب «ریسک اجرای ناقص»
نشان داده می‌شود.

در تولید سیگنال هم پایه‌ها **اتمی** پردازش می‌شوند: اگر یک پایه از
فیلتر ریسک رد نشود، کل ساختار صرف‌نظر می‌شود — چون نصف استردل، استردل
نیست.

**واحدها:** `bid/ask` در این پروژه **هر واحد** است و ضرب در
`contract_size` فقط یک بار در `strategies/payoff.py` انجام می‌شود.
کمیسیون پیش‌فرض **صفر** است چون نرخ واقعی در پروژه نیست — حدس نمی‌زنیم.

### انتخاب منبع داده

از تب «نمادها» قابل تنظیم است. چرا ایزی‌تریدر گزینه‌ی زنجیره نیست:

| داده | TSETMC | ایزی‌تریدر |
|---|---|---|
| زنجیره کامل (strike، سررسید، اندازه) | ✅ **یک** درخواست | ❌ هر ISIN یک درخواست |
| مظنه و موقعیت باز | ✅ | ✅ |
| وجه تضمین اولیه/لازم | ❌ | ✅ |
| **دامنه مجاز نوسان** | ❌ | ✅ |
| نیاز به لاگین | ❌ | ✅ |

ایزی‌تریدر مشخصات قرارداد را فقط از `/option/api/Contracts/{isin}/symbol`
می‌دهد — برای ۱۳۸۶ قرارداد بازار یعنی **حدود ۷ دقیقه در هر پاس**.

پس به‌جای «یا این یا آن»، ترکیب می‌شوند: زنجیره از TSETMC، و با
`enrich_with_broker` فقط چند قرارداد نزدیک به قیمت پایه از کارگزاری
غنی می‌شوند (وجه تضمین و اندازه‌ی دقیق قرارداد).

اگر کارگزاری در دسترس نباشد، زنجیره بدون غنی‌سازی برمی‌گردد و برچسب
منبع هم **ادعای دروغ نمی‌کند** (`tsetmc` می‌ماند، نه `tsetmc+emofid`).

### گزارش عملکرد

دکمه‌ی «ارزیابی سیگنال‌های در انتظار» قیمت فعلی هر سیگنال را از TSETMC
می‌خواند و نتیجه را در جدول `signal_outcomes` ثبت می‌کند.

طبقه‌بندی نتیجه عمداً محافظه‌کار است:

| وضعیت | یعنی |
|---|---|
| **برد** | حد سود خورده، یا سررسید گذشته و سود مثبت |
| **باخت** | حد ضرر خورده، یا سررسید گذشته و سود منفی |
| **در انتظار** | نه حد سود نه حد ضرر — معامله هنوز **باز** است |

سیگنالی که ۰.۲٪ پایین است شکست نخورده؛ شمردنش به‌عنوان باخت نرخ برد را
بی‌معنا می‌کند. به همین دلیل هم وقتی هیچ سیگنالی نتیجه نگرفته، نرخ برد
**«نامعلوم»** است نه صفر.

خروجی CSV با `utf-8-sig` نوشته می‌شود تا اکسل فارسی را درست باز کند.

هر سیگنال برچسب **منبع داده** دارد: `tsetmc+tsetmc` یعنی داده واقعی،
نوار بالای صفحه هم همین را نشان می‌دهد. این پروژه داده‌ی ساختگی ندارد،
پس منبع همیشه واقعی است.

⚠️ **داشبورد هیچ سفارشی ثبت نمی‌کند** و راهی به لایه‌ی `execution` ندارد؛ یک تست
گارد AST که کل مخزن را می‌پاید این را تضمین می‌کند.

🔒 فقط روی `127.0.0.1` گوش می‌دهد، یعنی از کامپیوترهای دیگر در دسترس نیست.
داشبورد **احراز هویت ندارد** و تنظیمات را می‌نویسد، پس روی شبکه بازش نکنید.
(`--host` وجود دارد ولی هشدار می‌دهد.)

### معیارهای عملکرد

نرخ برد به‌تنهایی گمراه‌کننده است. این مجموعه‌ی واقعی از بک‌تست را ببینید:

| استراتژی | نرخ برد | انتظار ریاضی | حداکثر افت |
|---|---|---|---|
| `directional_ma_cross` | ۵۹.۰٪ | **+۳.۱۲٪** | ۳۰۹٪ |
| `collar` | ۴۰.۷٪ | **−۱.۹۱٪** | ۶۸۶٪ |
| `neutral_iv_spread` | ۳۶.۷٪ | **−۲.۴۰٪** | ۱۶۱٪ |

نرخ برد ۴۰٪ در برابر ۵۹٪ تفاوت را نشان می‌داد، ولی **انتظار ریاضی** است
که می‌گوید دو استراتژی از سه‌تا در واقع پول از دست می‌دهند. یک زنجیره‌ی
**۴۵ باخت پشت‌سرهم** هم در همان اجرا دیده شد — عددی که میانگین کاملاً
پنهانش می‌کرد.

| معیار | چه چیزی را می‌گیرد |
|---|---|
| **انتظار ریاضی** | سود/زیان مورد انتظار هر سیگنال. نرخ برد بالا با زیان بزرگ = انتظار منفی |
| **ضریب سود** | مجموع بردها ÷ مجموع زیان‌ها؛ بیشتر از ۱ یعنی سودده |
| **Sharpe** | بازده به‌ازای واحد نوسان |
| **Sortino** | مثل Sharpe ولی فقط نوسانِ سمت زیان را جریمه می‌کند |
| **حداکثر افت** | بدترین افت از قله‌ی منحنی تجمعی — مسیری که میانگین پنهان می‌کند |
| **زنجیره باخت** | چند باخت پشت‌سرهم باید تحمل می‌کردید |
| **میانه** | برخلاف میانگین، یک سیگنال پرت جابه‌جایش نمی‌کند |

**یک پیاده‌سازی، دو مصرف‌کننده.** منطق در `backtest/metrics.py` است و هم
بک‌تست و هم گزارش زنده (`storage/reporting.py`) همان را صدا می‌زنند. جدا
نوشتنشان یعنی دو عدد مختلف برای «شارپ» بدون اینکه معلوم باشد کدام درست است.

**قرارداد `None`:** هر معیاری که نمونه‌ی کافی نداشته باشد `None` می‌دهد،
نه صفر. با یک نمونه، انحراف معیار **تعریف نشده** است؛ صفر برگرداندن یعنی
ادعای «بی‌ریسک». ضریب سود بدون هیچ زیانی هم `None` است، نه بی‌نهایت.

دو صداقتِ عمدی دیگر:

* **Sharpe سالانه‌سازی نشده** و اسمش هم `sharpe_per_signal` است. سالانه‌کردن
  به تعداد معامله در سال نیاز دارد که به بازه و تنظیمات وابسته است؛ ضرب در
  عددی حدسی، شارپ را دلبخواه بزرگ می‌کند.
* در بک‌تست، این اعداد روی **بازده جهت‌دار نماد پایه** حساب می‌شوند نه سود
  واقعی آپشن (اهرم لحاظ نشده). خودِ خلاصه هم این هشدار را چاپ می‌کند.
  گزارش زنده اما روی سود/زیان **واقعی** سیگنال‌های ارزیابی‌شده است.

سیگنال «در انتظار» از محاسبه کنار گذاشته می‌شود: معامله‌ای که هنوز باز
است نه برد است نه باخت، و صفر گرفتنش هم انتظار ریاضی و هم حداکثر افت را
رقیق و بی‌معنا می‌کند.

### اسپردهای عمودی و تقویمی

**چهار اسپرد عمودی** (هم‌سررسید، دو استرایک) از یک موتور مشترک می‌آیند.
نوشتنشان جدا یعنی چهار نسخه از یک منطق که با هم واگرا می‌شوند؛ فرقشان
فقط دو چیز است: نوع قرارداد، و اینکه پایه‌ی خریداری‌شده استرایک پایین‌تر
است یا بالاتر.

آنچه اسپرد را از پوزیشن تک‌پایه متمایز می‌کند، **محدود بودن هر دو طرف**
است — و همین در تست بررسی می‌شود: اگر `max_profit` یا `max_loss` مقدار
«نامحدود» بدهد، پایه‌ها اشتباه بسته شده‌اند.

یک گیت درستیِ مهم: ارزش اسپرد عمودی هرگز از `عرض × اندازه‌ی قرارداد`
بیشتر نمی‌شود. ساختاری که این قید را نقض کند رد می‌شود، چون یعنی
مظنه‌ها ناسازگارند (بازار رقیق) — **نه** اینکه فرصت آربیتراژ پیدا شده.
بدون این گیت، اسکنر در بازار رقیق ROIهای نجومی و جعلی گزارش می‌کرد.

#### ⚠️ اسپرد تقویمی: چرا سودش «نامعلوم» است

این مهم‌ترین نکته‌ی این بخش است. بقیه‌ی ساختارها یک سررسید دارند، پس
منحنی سود در سررسید دقیق است. اسپرد تقویمی این‌طور **نیست**: وقتی
پایه‌ی نزدیک منقضی می‌شود، پایه‌ی دور هنوز ارزش زمانی دارد — و کل سودِ
این ساختار همان است.

`StrategyPayoff` بر ارزش ذاتیِ سررسید بنا شده. اگر همان مدل را روی
اسپرد تقویمی اعمال کنیم، ارزش زمانیِ باقی‌مانده صفر فرض می‌شود و نتیجه
این می‌شود:

```
strike=500 call gap=28d cost=17,000
   max_profit = -17,000     ROI = -1.0      ← غلط، نه «دست‌کم گرفته‌شده»
```

یعنی یک اسپرد تقویمیِ سالم به‌عنوان **زیان کامل** گزارش می‌شد.

پس `StrategyPayoff` یک فلگ `single_expiry` گرفت. با `False`:

| مقدار | نتیجه |
|---|---|
| `max_profit`, `max_loss`, `roi`, `risk_reward`, `breakevens` | `None` — «نمی‌دانیم» |
| `net_cost`, `net_premium` | **دقیق می‌مانند** (هزینه‌ی ورود واقعی است) |

و اسپردهای تقویمی بر اساس **هزینه** مرتب می‌شوند، نه ROI. در داشبورد هم
یک چیپ هشدار می‌خورند و `null` آن‌جا «نامعلوم» خوانده می‌شود، نه
«نامحدود» — این دو را یکی گرفتن همان اشتباه را از راه دیگری تکرار می‌کرد.

محاسبه‌ی درستش به قیمت‌گذاری پایه‌ی دور در تاریخ سررسید نزدیک نیاز دارد،
یعنی یک فرض دربارهٔ IV آینده. تا آن موقع، **نگفتن** بهتر از عددی است که
قابل مقایسه به نظر بیاید ولی نباشد.

#### تنها منبع حقیقتِ فهرست ساختارها

`SCAN_KINDS` در `strategies/scanner.py` تنها جایی است که ساختارها فهرست
می‌شوند؛ `scan_all`، API و dropdown داشبورد همه از آن ساخته می‌شوند.
قبلاً سه فهرست موازی بود (اسکنر، `web/api.py`، `app.js`) که یعنی یک روز
اسکنری اضافه می‌شد و داشبورد هرگز نشانش نمی‌داد.

افزودن ساختار تازه = یک متد `scan_x` + یک ورودی در `SCAN_KINDS`. یک تست
هم بررسی می‌کند این دو از هم جدا نیفتند.

### شرط مالکیت برای Covered Call

Covered Call یعنی فروش کال روی سهمی که **داری**. بدون سهم، همان معامله یک
**کالِ لخت** است:

| | سود | زیان |
|---|---|---|
| Covered Call (با سهم) | محدود، سقف‌دار | افت سهم منهای پرمیوم |
| کالِ لخت (بدون سهم) | محدود به پرمیوم | **نامحدود** |

این دو یک استراتژی با پارامتر مختلف نیستند. قبلاً فقط یک جمله‌ی هشدار در
متن سیگنال بود؛ حالا اگر بدانیم سهم نداری، سیگنال **صادر نمی‌شود**.

**سه حالت، و تفاوت‌شان تصمیم‌ساز است:**

| `underlying_holding` | یعنی | رفتار |
|---|---|---|
| `None` | نامعلوم (کارگزاری خاموش) | سیگنال با هشدار — مثل قبل |
| کمتر از یک قرارداد | می‌دانیم کافی نیست | **رد** |
| کافی | می‌دانیم چقدر داری | سیگنال + تعداد قرارداد قابل پوشش |

تفکیک «نامعلوم» از «ندارد» عمدی و مهم است: اگر یک تایم‌اوت گذرا به «سهم
نداری» ترجمه می‌شد، همه‌ی سیگنال‌های Covered Call بی‌صدا حذف می‌شدند و
کاربر هیچ‌وقت نمی‌فهمید چرا. پس شکستِ خواندن هرگز صفر نمی‌شود.

```yaml
strategies:
  neutral_iv_spread:
    params:
      require_underlying_holding: true            # مالکیتِ ناکافی ⇒ رد
      skip_covered_call_if_holding_unknown: false # نامعلوم هم رد شود؟
```

**مرزِ معماری:** استراتژی یک **عدد** می‌گیرد
(`StrategyContext.underlying_holding`)، نه کلاینت کارگزاری. استراتژی حق
دسترسی به شبکه و حساب را ندارد و گاردِ AST همین را تست می‌کند — پس لایه‌ی
wiring دارایی را می‌خواند و به‌صورت داده پاس می‌دهد.

اندازه‌ی قرارداد از خودِ زنجیره می‌آید، نه از عددِ ثابت ۱۰۰۰: نمادی با
اندازه‌ی متفاوت وگرنه بی‌صدا غلط حساب می‌شد.

دارایی یک بار در هر پاس خوانده می‌شود (یک پاسخ همه‌ی نمادها را دارد) و
بین پاس‌ها کش نمی‌ماند — کاربر ممکن است وسط دو پاس سهم بخرد.

⚠️ مثل بقیه‌ی مسیرهای کارگزاری، روی حساب زنده تست نشده.

### دارایی حساب از کارگزاری

`account_equity` در yaml یک عدد دستی بود، و عدد دستی سریع کهنه می‌شود:
ریسک روی دارایی‌ای اندازه‌گیری می‌شد که دیگر وجود نداشت.

با روشن‌کردن `risk.use_broker_equity`، موجودی از
`GET /easy/api/money` خوانده می‌شود. بورس تهران تسویه‌ی T+۰/T+۱/T+۲ دارد،
پس «موجودی» یک عدد نیست:

| مقدار | معنی |
|---|---|
| `buy_power_t2` | قدرت خرید با احتساب پول تسویه‌نشده |
| `cash_t0` … `cash_t2` | نقد در هر مرحله‌ی تسویه |
| `margin_blocked` | وجه تضمین موقعیت‌های باز آپشن |

`equity` عمداً روی **قدرت خرید T+۲** بسته می‌شود: محافظه‌کارانه‌ترین
تعریفی که وجه بلوکه‌شده را کنار می‌گذارد. اگر کارگزاری آن را نفرستد،
به نقدِ T+۲ برمی‌گردد.

سه قید عمدی:

| حالت | رفتار |
|---|---|
| پیش‌فرض | **خاموش** — رفتار فعلی کسی بی‌خبر عوض نمی‌شود |
| خطای شبکه / توکن منقضی | بازگشت به عدد yaml + لاگ هشدار |
| موجودی صفر یا منفی | عدد yaml نگه داشته می‌شود |

قید سوم مهم است: حساب صفر یعنی هر سیگنال صفر قرارداد می‌گیرد، که فرقی با
نبودِ سیگنال ندارد ولی شبیه یک اشکال نرم‌افزاری به نظر می‌آید.

در تب **حساب** موجودی دیده می‌شود و در تب **ریسک** سوئیچش هست.

⚠️ **این مسیر روی حساب زنده تست نشده.** پیاده‌سازی روی شکل پاسخِ
ضبط‌شده‌ی سشن واقعی است (`docs/broker-emofid.md`)، و تست‌ها همان شکل را
می‌پوشانند — ولی خودِ درخواست هنوز به حساب واقعی نرفته است.

### تعدیل رویداد شرکتی

وقتی نماد پایه افزایش سرمایه می‌دهد، قیمت سهم به تناسب کاهش می‌یابد ولی
ارزش کل موقعیت نباید تغییر کند. بورس تهران همان روز استرایک و اندازه‌ی
قرارداد را تعدیل می‌کند. اگر ما تعدیل نکنیم:

* قیمت پایه یک‌شبه مثلاً یک‌هشتم می‌شود،
* استرایکِ **قدیم** با قیمتِ **جدید** مقایسه می‌شود،
* هر کالِ در-سود ناگهان عمیقاً بی‌ارزش به نظر می‌آید.

یک موج سیگنالِ کاملاً غلط، دقیقاً در پرنوسان‌ترین روز. این خطا بی‌صداست:
هیچ‌چیز نمی‌شکند، فقط اعداد غلط می‌شوند.

**فرمول** — نسبت = سهام قدیم ÷ سهام جدید

| مقدار | تعدیل |
|---|---|
| استرایک | × نسبت |
| اندازه قرارداد | ÷ نسبت |

یعنی `استرایک × اندازه` ثابت می‌ماند — همان قیدی که کل تعدیل بر پایه‌ی آن
تعریف شده، و صریح تست می‌شود. برای **سود نقدی** فرمول فرق دارد: استرایک
به اندازه‌ی مبلغ سود کم می‌شود و اندازه‌ی قرارداد دست‌نخورده می‌ماند.

**مرز مهم:** تعدیل فقط برای قراردادهایی معنا دارد که **قبل از** رویداد
نوشته شده‌اند. قراردادی که بعد از افزایش سرمایه منتشر شده، استرایکش از
اول تعدیل‌شده است؛ تعدیل دوباره خرابش می‌کند. پس `adjust` تاریخ انتشار
می‌گیرد و فقط رویدادهای بعد از آن را اعمال می‌کند.

**اثر روی بک‌تست** — اینجا خطا واقعاً گران بود. تاریخچه‌ی خام خودرو:

| تاریخچه | بزرگ‌ترین افت روزانه |
|---|---|
| خام | **−۸۳٫۸٪** در ۲۰۲۵-۰۴-۲۲ (ریزش ساختگی) |
| تعدیل‌شده | −۲۶٫۲٪ (یک حرکت واقعی) |

آن ریزش ۸۴٪ هرگز رخ نداده؛ فقط روزِ افزایش سرمایه است. هر استراتژی
تکنیکالی آن را سیگنال نزولیِ قوی می‌فهمد و کل نتیجه‌ی بک‌تست بی‌معنا
می‌شود. بک‌تست حالا تاریخچه را پیش از اجرا تعدیل می‌کند
(`backtest.adjust_corporate_actions`، پیش‌فرض روشن).

**منبع:** endpoint عمومی `GetInstrumentShareChange` با `numberOfShareOld`
و `numberOfShareNew`. برای سود نقدی، TSETMC منبع عمومیِ قابل‌اتکایی
نمی‌دهد، پس این نوع رویداد فقط دستی ثبت می‌شود — حدس نمی‌زنیم.

⚠️ یک تله‌ی واقعی: TSETMC گاهی یک رویداد را **دو روز پشت‌سرهم** گزارش
می‌کند (روی وبملت دیده شد). یکتاسازی روی خودِ گذارِ سهام انجام می‌شود نه
تاریخ، وگرنه نسبت دوبار اعمال می‌شد و استرایک نصفِ نصف می‌شد.

### عمق مظنه

تا اینجا فقط **بهترین** مظنه‌ی خرید/فروش را داشتیم. با یک سطح، این سؤال
بی‌جواب می‌ماند:

> اگر ۱۰ قرارداد بخرم، واقعاً به چه قیمتی پر می‌شود؟

در بازار آپشن تهران این سؤال حیاتی است. نمونه‌ی واقعی از همین بازار:

| سطح | بهترین فروش | حجم |
|---|---|---|
| ۱ | ۳۳٬۸۰۰ | **۱ قرارداد** |
| ۲ | ۳۴٬۰۰۰ | ۱۰۱ |
| ۳ | ۳۴٬۹۵۰ | ۵ |

نماد «۳۳٬۸۰۰» را نشان می‌دهد، ولی فقط برای یک قرارداد. سفارش ۱۰ تایی با
میانگین ۳۳٬۹۸۰ پر می‌شود و سفارش ۱۰٬۰۰۰ تایی **اصلاً پر نمی‌شود** —
کل عمق ۱۱۱ قرارداد است. سیگنالی که با مظنه‌ی سطح‌اول اندازه‌گیری شده،
روی کاغذ سودده است و در عمل با لغزش اجرا می‌شود.

`data/order_book.py` از endpoint عمومی `BestLimits` پنج سطح را می‌گیرد و
می‌گوید:

| پرسش | متد |
|---|---|
| با این حجم چه قیمتی پر می‌شود؟ | `fill_price(side, qty)` |
| چقدر بدتر از سطح اول؟ | `slippage(side, qty)` |
| اصلاً پر می‌شود؟ | `can_fill(side, qty)` |
| کل عمق یک سمت | `depth(side)` |

خریدِ ما روی **فروش**های دفتر پر می‌شود و برعکس؛ این وارونگی در یک جا
متمرکز شده و صریح تست می‌شود.

اگر سفارش پر نشود، `slippage` عمداً `None` برمی‌گرداند نه یک عدد
خوش‌بینانه — بهتر است بدانیم پر نمی‌شود تا اینکه فکر کنیم ارزان پر شده.

در تب **ساختارها**، تیکِ «عمق مظنه» را بزنید تا ستون عمق به نقشه‌ی سفارش
اضافه شود. پیش‌فرض خاموش است چون هر پایه یک درخواست جدا به TSETMC می‌خورد.

### قرارداد منبع مظنه

`OrderBookClient` روی **پولینگ** کار می‌کند: هر بار یک درخواست HTTP. برای
رباتی که هر ۵ دقیقه پاس می‌زند کافی است. ایزی‌تریدر اما یک اتصال
Lightstreamer دارد که همان داده را **push** می‌کند.

اگر هسته مستقیم به کلاینت TSETMC وصل بود، افزودن آن مسیر یعنی تغییر در
همه‌ی مصرف‌کننده‌ها. با `data/quote_source.py::RealtimeQuoteSource`، یعنی
یک پیاده‌سازی تازه که همین سوئیت تست را پاس کند.

| ویژگی | معنی |
|---|---|
| `get_order_book()` | دفتر سفارش؛ خطا را **بالا می‌برد** |
| `try_get_order_book()` | همان، ولی خطا را می‌بلعد (در خودِ قرارداد) |
| `is_push` | پولینگ یا push؟ مصرف‌کننده با همین تصمیم می‌گیرد هر چند وقت بپرسد |

`try_get_order_book` در **خودِ قرارداد** پیاده شده، نه در هر آداپتر: یک
پیاده‌سازی تازه فقط `get_order_book` را لازم دارد و رفتار «عمق یک افزونه
است، نبودش پاس رصد را نمی‌خواباند» را رایگان می‌گیرد.

#### یک پارسر، دو مصرف‌کننده

هنگام افزودن عمق مظنه، پاسخ `BestLimits` **دو جا** نگاشت می‌شد: یک بار
در `tsetmc_quote_client.py` (که از قبل بود و جایی استفاده نمی‌شد) و یک بار
در `order_book.py`. دو نگاشت موازی از یک پاسخ دیر یا زود واگرا می‌شوند و
بعد دو عدد مختلف برای «بهترین مظنه» می‌دهند.

حالا `parse_best_limits` تنها جای نگاشت است و `OrderBook` فقط **منطق** را
اضافه می‌کند («با این حجم چه قیمتی پر می‌شود»). یک تست بررسی می‌کند هر دو
مسیر دقیقاً یک دفتر سفارش بدهند.

### تقویم معاملاتی

قبلاً «بازار باز است؟» فقط پنجشنبه و جمعه را تعطیل می‌دانست. یعنی در
نوروز و عاشورا هم ربات پاس رصد می‌زد و روی مظنه‌ی **دیروز** سیگنال
می‌ساخت — سیگنالی با قیمت بیات، که از سیگنال نداشتن بدتر است.

حالا `market/trading_calendar.py` تعطیلات را **از خودِ بازار** یاد
می‌گیرد: هر روزِ کاریِ غیرآخرهفته که در تاریخچه‌ی واقعی TSETMC کندلی
ندارد، تعطیل بوده.

چرا این‌طور و نه با یک جدول دستی؟ تعطیلات ایران دو دسته‌اند:

| دسته | مثال | مشکلش |
|---|---|---|
| شمسی-ثابت | ۱۳ فروردین، ۲۲ بهمن | هر سال سر جای خودش — قابل جدول‌کردن |
| قمری-متحرک | تاسوعا، عاشورا، اربعین | هر سال ~۱۱ روز جلو می‌آید — جدول دستی هر سال کهنه می‌شود |

پس دسته‌ی دوم را فقط بازار می‌داند. جدول شمسی-ثابت صرفاً برای روزهای
**آینده** به کار می‌رود که هنوز تاریخچه‌ای ندارند.

ترتیب تصمیم:

1. پنجشنبه/جمعه → تعطیل (قطعی، بدون نیاز به داده)
2. تعطیلیِ یادگرفته‌شده از تاریخچه‌ی واقعی → معتبرترین منبع
3. جدول شمسی-ثابت → فقط بیرون بازه‌ی تاریخچه

نتیجه روی داده‌ی زنده: **۳۶ روز تعطیل** در یک سال گذشته، شامل نوروز
۱۴۰۵ و تعطیلات قمری‌ای که هیچ جدول ثابتی نمی‌توانست بداند.

```yaml
trading_calendar:
  learn_from_market: true      # یادگیری از تاریخچه واقعی
  reference_symbol: خودرو      # نماد مرجع؛ باید پرمعامله باشد
  learn_days: 365
  cache_path: var/trading_calendar.json
  extra_holidays: []           # تعطیلی اضطراری که هنوز در تاریخچه نیامده
```

نماد مرجع باید پرمعامله باشد، وگرنه «نبودِ کندل» یعنی توقف نماد، نه
تعطیلی بازار. شکست یادگیری (قطعی شبکه) خطا نمی‌دهد و به رفتار قبلی
(فقط آخرهفته) برمی‌گردد — نداشتن تقویم دقیق نباید کل پاس رصد را بخواباند.

تبدیل تاریخ شمسی هم داخل همین ماژول است (بدون وابستگی خارجی) و رفت‌وبرگشتش
روی ۳۰ سال تست شده.

## Getting Started

### ۰. آماده‌سازی محیط (یک بار)

```powershell
cd D:\Project\github\GarnetTrader\option_signal_bot

py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt

copy config\settings.example.yaml config\settings.yaml
```

آخرین خط برای اجرای با **داده واقعی** لازم است. بدون فایل تنظیمات، ربات روی
پیش‌فرض‌های داخلی کار می‌کند (که آن‌ها هم واقعی‌اند).

⚠️ **دو نکته که بیشترین خطا را می‌سازند:**

| نکته | چرا |
|---|---|
| **در پوشه‌ی `option_signal_bot` باشید**، نه ریشه‌ی ریپو | `main.py` و `.venv` اینجا هستند. از ریشه، خطای `could not be loaded` می‌گیرید. |
| در PowerShell **`.\`** را جا نیندازید | `.venv\...` را PowerShell اسم ماژول می‌فهمد و `Import-Module` پیشنهاد می‌دهد. `.\.venv\...` درست است. |

راه ساده‌تر — یک بار محیط را فعال کنید و بعد `python` خالی کافی است.

⚠️ **این دو خط، دو دستور جداگانه‌اند.** اول این را بزنید و **Enter**:

```powershell

```

اگر درست کار کرد، پیش‌وند `(.venv)` به prompt اضافه می‌شود:

```
(.venv) PS D:\Project\github\GarnetTrader\option_signal_bot>
```

**بعد** دستور بعدی را بزنید:

```powershell
python main.py --dry-run
```

اگر هر دو را در **یک خط** بنویسید، PowerShell دومی را آرگومانِ `Activate.ps1`
می‌فهمد و خطای `A positional parameter cannot be found` می‌دهد.

اگر PowerShell اجازه‌ی اسکریپت نداد:
`Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass`

### ۳. تنظیمات

```bash
cp config/settings.example.yaml config/settings.yaml
```

فایل نمونه از پیش روی داده **واقعی** TSETMC تنظیم شده (`provider: tsetmc`).
کافی است:
- `market_data.symbols` را با نمادهایی که آپشن دارند پر کنید
  (لیست را با `.\.venv\Scripts\python.exe scripts/fetch_tsetmc_sample.py` ببینید)
- `risk.*` را با اندازه حساب خودتان تنظیم کنید
- برای اجرای آفلاین، `provider` را `fixture` بگذارید (پاسخ ضبط‌شده‌ی واقعی)

**توکن تلگرام** را در فایل ننویسید؛ از متغیرهای محیطی استفاده کنید
(مقدار متغیر محیطی بر مقدار فایل اولویت دارد):

```bash
set TELEGRAM_BOT_TOKEN=123456:ABC...
set TELEGRAM_CHAT_ID=-1001234567890
```

و در `settings.yaml` مقدار `notifiers.telegram.enabled` را `true` کنید.
`config/settings.yaml` در `.gitignore` است تا توکن به گیت نرود.

⚠️ **`settings.yaml` را با `Set-Content` یا `Out-File` ویرایش نکنید.** این‌ها
کامنت‌های فارسی فایل را خراب می‌کنند (double-encode + BOM) و بعدش ربات با یک
traceback خام از PyYAML می‌افتد:
`yaml.reader.ReaderError: unacceptable character #x0081`.

برای ویرایش از VS Code یا Notepad++ استفاده کنید (با encoding **UTF-8 بدون BOM**).
اگر فایل خراب شد، دوباره بسازیدش:

```powershell
Remove-Item config\settings.yaml
copy config\settings.example.yaml config\settings.yaml
```

### ۶. داده واقعی بازار (بدون لاگین و بدون توکن)

زنجیره آپشن و تاریخچه نماد پایه از **API عمومی TSETMC** می‌آید؛ هیچ احراز هویتی،
کوکی یا حساب کارگزاری لازم نیست:

| داده | endpoint |
|---|---|
| زنجیره کامل آپشن بازار (یک درخواست) | `cdn.tsetmc.com/api/Instrument/GetInstrumentOptionMarketWatch/{market}` |
| تاریخچه روزانه نماد پایه | `cdn.tsetmc.com/api/ClosingPrice/GetClosingPriceDailyList/{insCode}/0` |

هر ردیف پاسخ دیده‌بان، یک استرایک با **جفت** کال و پوت است و قیمت لحظه‌ای نماد پایه
(`pDrCotVal_UA`) و کد یکتای آن (`uaInsCode`) را هم دارد. نتیجه:

- کل بازار با یک درخواست می‌آید، نه یکی به‌ازای هر نماد
- قیمت پایه و پرمیوم آپشن از **یک پاسخ و یک لحظه**اند (اختلاف منبع، محاسبه IV را خراب می‌کند)
- نگاشت نماد→`insCode` از همان پاسخ ساخته می‌شود؛ به جدول نماد جداگانه نیازی نیست

دیدن لیست نمادهایی که آپشن دارند و وضعیت بازار:

```bash
.\.venv\Scripts\python.exe scripts/fetch_tsetmc_sample.py                 # گزارش
.\.venv\Scripts\python.exe scripts/fetch_tsetmc_sample.py --save-fixture  # به‌روزرسانی نمونه تست
```

**سه لایه داده** پشت همان اینترفیس، با `option_chain.provider` انتخاب می‌شوند:

| provider | داده | کاربرد |
|---|---|---|
| `tsetmc` | زنده | اجرای واقعی |
| `fixture` | پاسخ واقعی **ضبط‌شده** | تست آفلاین، بازتولید یک روز خاص |

**گیت‌های کیفیت داده** (`option_chain.quality`) لازم‌اند، نه تشریفاتی: در یک اجرای
واقعی روی خودرو، ۲۳ قرارداد از ۷۸ حذف شد (۱۱ اسپرد پهن، ۱۲ بدون موقعیت باز).
هر حذف در لاگ شمرده می‌شود تا بی‌صدا نباشد.

### ۷. کشف API پلتفرم کارگزاری (ایزی‌تریدر / emofid)

آدرس درست پلتفرم **`easytrader.ir`** است (متعلق به مفید، و ارجاع‌دهنده به `emofid.com`).
⚠️ `easytrader.com` یک صفحه‌ی **فروش دامنه**ی بی‌ربط است؛ هرگز اعتبارنامه‌تان را آن‌جا وارد نکنید.

TSETMC داده‌ی بازار را می‌دهد ولی سه چیز را نمی‌دهد: **پوزیشن و موجودی حساب**،
**عمق مظنه**، و **push زیرثانیه**. برای آن‌ها به سشن احرازهویت‌شده‌ی کارگزاری نیاز است.
گام اول، کشف سطح API است — با دو مسیر:

> ⏰ **حتماً در ساعت بازار اجرا کنید** (شنبه–چهارشنبه، ~۹:۰۰ تا ۱۲:۳۰).
> در بازار بسته، دیده‌بان و عمق مظنه هیچ داده‌ای push نمی‌کنند و گزارش تقریباً خالی
> درمی‌آید. تست‌شده: اجرای یک‌دقیقه‌ای بیرون ساعت بازار فقط ۲ endpoint داد که
> هر دو آنالیتیکس بودند.

**مسیر ۱ — مرورگر قابل‌مشاهده (توصیه‌شده)**

نصب یک‌باره:
```bash
.\.venv\Scripts\python.exe -m pip install playwright
```
اگر Chrome سیستم را دارید، به `playwright install` نیازی نیست؛ اسکریپت با
`channel="chrome"` همان Chrome خودتان را می‌راند (بدون دانلود ~۴۰۰ مگابایتی).

اجرا:
```bash
.\.venv\Scripts\python.exe scripts/emofid_login.py --url https://easytrader.ir --minutes 15
```

چه اتفاقی می‌افتد:
1. یک پنجره‌ی واقعی Chrome باز می‌شود و به `easytrader.ir` می‌رود
2. **خودتان** نام کاربری، رمز و OTP را وارد می‌کنید — اسکریپت هیچ فرمی پر نمی‌کند
3. بعد از لاگین، این صفحات را باز کنید (هرچه بیشتر، فهرست کامل‌تر):
   **دیده‌بان بازار آپشن**، **سبد دارایی/پوزیشن**، **موجودی حساب**،
   **عمق مظنه یک نماد آپشن**
4. برای پایان زودتر از ۱۵ دقیقه: `Ctrl+C`

**مسیر ۲ — بدون هیچ نصبی (HAR)**

اگر نمی‌خواهید playwright نصب کنید یا مرورگر را به اسکریپت بسپارید:

1. Chrome → `F12` → تب **Network**
2. تیک **«Preserve log»** را بزنید
3. لاگین کنید و همان صفحات بالا را باز کنید
4. راست‌کلیک روی لیست درخواست‌ها → **«Save all as HAR with content»**
5. سپس:

```bash
.\.venv\Scripts\python.exe scripts/har_to_inventory.py مسیر\فایل.har
```

خروجی هر دو مسیر یکی است: `var/emofid/api_inventory.md` و `.json`.

**بعد از اجرا، این‌ها را در گزارش نگاه کنید:**

```bash
type var\emofid\api_inventory.md
```

- هر endpoint مربوط به **پوزیشن / موجودی / سبد** → ورودی آداپتر `AccountDataSource`
- **اتصال سوکت** (SignalR/WebSocket) → مسیر `RealtimeQuoteSource` برای push زیرثانیه
- **هدرهای احراز هویت** (`authorization` یا `cookie`) → نحوه‌ی نگه‌داشتن سشن

**تضمین حریم خصوصی — «شکل را ضبط کن، نه داده را»:** برای نوشتن آداپتر، نام فیلدها
و نوعشان کافی است؛ مقدار موجودی و توکن هیچ‌وقت لازم نیست. پس:

| داده | چه چیزی ثبت می‌شود |
|---|---|
| بدنه‌ی پاسخ | فقط اسکلت نوع‌ها: `{"balance": "number"}` نه `{"balance": 987654321}` |
| هدر احراز هویت | فقط **نوعش**: `Bearer <REDACTED>` |
| شناسه در مسیر URL | `/accounts/<NUM>/positions` |
| پارامتر حساس در query | `token=<REDACTED>` (ولی `type=option` می‌ماند چون مفید است) |
| فریم SignalR | فقط نام متد (`OnBestLimitChanged`)، نه آرگومان‌ها |

این تضمین **تست دارد**: `tests/test_api_inventory.py` یک HAR ساختگی با توکن و کد ملی و
موجودی جعلی می‌سازد و بررسی می‌کند هیچ‌کدام در خروجی نباشند.

⚠️ دو فایل حساس‌اند و زیر `var/` (در `.gitignore`) می‌مانند: `session.json`
(معادل دسترسی به حساب) و فایل HAR خام. **گزارش خروجی** قابل اشتراک است، ولی
قبلش یک مرور چشمی بکنید.

### مایل‌استون ۵.۲ — حسابداری قابل اتکای معاملات کاغذی

هدف: بشود استراتژی‌ها را بدون پول واقعی **ارزیابی** کرد. تا پیش از این
عددهای پنل حساب قابل تطبیق نبودند.

**رابطه‌ی مبنا — یکی، و همه‌جا همان:**

```
ارزش کل حساب = وجه نقد + ارزش روز موقعیت‌های باز

ارزش کل حساب − سرمایه‌ی اولیه
      = سود تحقق‌یافته‌ی خالص + سود تحقق‌نیافته‌ی خالص
```

اتحاد دوم در هر پاسخِ `/api/paper-trading/account` به‌صورت
`reconciliation` سنجیده می‌شود. اگر نخواند، پنل صریح می‌گوید به اعداد
تکیه نکنید.

| پیش از این | حالا |
|---|---|
| `equity = نقد + سود شناور` — ارزشِ خودِ موقعیت جا می‌افتاد، پس لحظه‌ی ورود زیانِ موهوم نشان می‌داد | `equity = نقد + ارزش روز` |
| خرید بدون هیچ کنترل نقدینگی؛ نقد منفی می‌شد | سفارشِ بدون وجه **پیش از** هر تغییری رد می‌شود |
| کارمزد ورود در P&L معامله‌ی بسته‌شده نمی‌آمد | کارمزد ورود روی موقعیت می‌نشیند و با هر خروج به نسبت منتقل می‌شود — هر هزینه دقیقاً یک بار |
| `pnl_pct = (خروج−ورود)/ورود` — بدون کارمزد و بدون اندازه | `return_on_cost_pct` = خالص ÷ سرمایه‌ی درگیر |
| افت از جمع ساده‌ی درصدها | `account_drawdown` ریالی روی منحنی حساب، از **قله‌ی مرتبط** — جدا از معیارِ سطح سیگنال |
| موقعیتِ بدون قیمت بی‌صدا از جمع حذف می‌شد | وضعیت صریح؛ ارزش کل حساب «نامشخص» می‌شود و با صفر پر نمی‌شود |
| سررسید خودکار با آخرین پرمیومِ معامله‌شده تسویه می‌شد | تا تعیین تکلیف `expired_unsettled` می‌ماند؛ سفارش عادی هم روی قرارداد سررسیدشده رد می‌شود |
| هر نوشتن جدا commit می‌شد | هر عملیات مالی داخل یک تراکنش؛ شکستِ وسط کار حساب را نیمه‌تغییرکرده نمی‌گذارد |

**تعیین تکلیف سررسید — «فرضِ کاربر»، نه تسویه‌ی رسمی**

قواعد اعمال و تسویه‌ی بورس تهران در این پروژه **پیاده نشده‌اند** و
هزینه‌ی خودِ تسویه هم مدل نشده است. کاری که دکمه‌ی «تسویه» می‌کند فقط
ثبتِ عددی است که **شما فرض می‌کنید**، تا حساب بسته شود و ارزش‌گذاری معلق
نماند.

* عدد ورودی **پرمیوم هر واحد** است، نه ارزش کل قرارداد؛ ارزش کل از
  `قیمت × تعداد × اندازه‌ی قرارداد` در می‌آید.
* صفر مقدارِ معتبری است (انقضای بی‌ارزش) ولی باید **صریح** وارد شود:
  فیلد خالی یا فقط فاصله، صفر تفسیر نمی‌شود.
* `inf` و `nan` هم در API و هم در لایه‌ی مالی رد می‌شوند.
* سفارش عادی (خرید یا فروش) روی قرارداد گذشته از سررسید **رد** می‌شود،
  حتی اگر منبع هنوز برایش دفتر سفارش بدهد. مسیر تعیین تکلیف دستی جداست.

**«هزینه دانسته است» به خودِ همان عملیات وابسته است**

نرخی که امروز در تنظیمات می‌نشیند چیزی درباره‌ی هزینه‌ی معامله‌ی دیروز
نمی‌گوید. پس دو پرچمِ جدا وجود دارد:

| پرچم | یعنی |
|---|---|
| `rates_configured` | نرخ‌ها دانسته‌اند — فقط درباره‌ی معامله‌های **بعدی** |
| `costs_known` | هزینه‌ی **همه‌ی** عملیات‌های ثبت‌شده دانسته است |

تا `costs_known` نادرست باشد، هیچ «خالصِ قطعی» نمایش داده نمی‌شود
(`realized_net` و `unrealized_net` برابر `None`) — ولی ناخالص و
هزینه‌های ثبت‌شده همچنان درست و قابل نمایش‌اند، و `equity` که به هزینه
وابسته نیست، عدد خودش را دارد.

**صفرِ پیش‌فرض ≠ صفرِ اعلام‌شده.** نرخ پیش‌فرض پروژه صفر است، ولی آن صفر
یعنی «نمی‌دانیم»، نه «هزینه‌ای نیست». پس معامله‌ای که زیر نرخِ
تنظیم‌نشده انجام شود، هزینه‌اش **نامعلوم** ثبت می‌شود. اگر کارگزاری شما
واقعاً کارمزد ندارد، تیکِ «این نرخ‌ها را خودم وارد کرده‌ام» را بزنید
(`paper_trading.fees.declared: true`) تا صفرِ شما هزینه‌ی دانسته شمرده
شود.

وضعیتِ «دانسته بودن» هنگام **همان عملیات** روی ردیف می‌نشیند — هم برای
کارمزد ورود و هم خروج — و در خرید افزایشی، خروج جزئی، خروج کامل و
تعیین تکلیف سررسید حفظ می‌شود. تنظیم نرخ در آینده سابقه را معلوم
نمی‌کند؛ فقط روی معامله‌های بعدی اثر دارد.

**وضعیت ارزش‌گذاری هر موقعیت** (`execution/paper_account.py`):

| وضعیت | یعنی |
|---|---|
| `ok` | عمق سمت خرید برای خروجِ کل موقعیت کافی بود |
| `partial_depth` | عمق فقط بخشی را می‌خرد؛ قیمت مرجع داده می‌شود ولی در جمع حساب نمی‌آید |
| `no_depth` | سمت خریدِ دفتر خالی است |
| `unavailable` | دفتر سفارش در دسترس نبود |
| `expired_unsettled` | سررسید گذشته و تسویه نشده |

**مرزهای باقی‌مانده — عمداً باز:**

- **فقط long تک‌پایه.** فروش استقراضی و ساختارهای چندپایه (استردل،
  کولار) مدل نشده‌اند و سفارششان **رد** می‌شود. وجه تضمین بورس تهران در
  پروژه نیست و حدس زده نمی‌شود؛ ریسکِ ساختار کامل با ریسکِ یک پایه یکی
  نیست.
- **مبلغ مسدود همیشه صفر است** — سفارش معلق وجود ندارد (هر سفارش فوری
  حل می‌شود) و وجه تضمینی هم مدل نشده. عدد نمایش داده می‌شود تا «صفر» با
  «حساب‌نشده» اشتباه نشود.
- **نرخ کارمزد، مالیات و قواعد تسویه حدس زده نمی‌شوند.** با نرخ صفر،
  پنل صریح می‌گوید «هزینه مشخص نشده» و «خالص» همان «ناخالص» است.
- **افت حساب فقط از معاملات بسته‌شده** حساب می‌شود؛ افتی که در دلِ یک
  موقعیتِ باز رخ داده و تحقق نیافته، در آن نیست.
- **معاملات پیش از این نسخه** سهم کارمزد ورودشان ثبت نشده بود؛ در
  مهاجرت `NULL` ماند (نه صفر) و پنل تعدادشان را اعلام می‌کند.

**مهاجرت پایگاه:** اسکیمای `paper_trading.db` به **نسخه ۳** رفت.
ستون‌ها با `ALTER TABLE` اضافه می‌شوند و هیچ ردیفی حذف یا بازنویسی
نمی‌شود.

* نسخه ۲ — تفکیک هزینه‌ی ورود و خروج. `gross_pnl` و `exit_fee` برای
  ردیف‌های قدیمی از روی `pnl_absolute + fee_paid` بازسازی می‌شوند؛
  `entry_fee` دانسته نیست و `NULL` می‌ماند.
* نسخه ۳ — `entry_fees_known` روی موقعیت‌ها. ستون عددی `entry_fees`
  نمی‌توانست `NULL` بگیرد، پس موقعیت‌هایی که پیش از ارتقا وجود داشتند
  «نامعلوم» علامت می‌خورند. بدون این، صفرِ پیش‌فرضِ مهاجرت از صفرِ واقعی
  قابل تشخیص نبود.

**افتِ سرمایه:** درصدِ افت از **قله‌ی مربوط به همان افت** حساب می‌شود، نه
از سرمایه‌ی اولیه — ۱۰۰ → ۲۰۰ → ۱۵۰ یعنی افتِ مبلغی ۵۰ و افتِ درصدی
۲۵٪. بیشترین افتِ مبلغی و بیشترین افتِ درصدی لزوماً یک‌جا نیستند، پس هر
دو با زمانِ خودشان گزارش می‌شوند. با فیلتر بازه، منحنی از **مانده‌ی
ابتدای همان بازه** شروع می‌شود.

### مایل‌استون ۵.۳ — غربال قابلیت معامله

پژوهش و تصمیم‌ها در [`docs/strategy-research.md`](../docs/strategy-research.md).

**مسئله:** در یک snapshot واقعیِ ثبت‌شده (۲۰۲۶-۰۹-۱۱، ۱۴۳۲ قرارداد)، فقط
**۳۷٪** قراردادها هر دو مظنه دارند و **۱۸٪** اصلاً مظنه‌ی خرید ندارند —
یعنی خروج از آن‌ها ممکن نیست. سیگنال روی چنین قراردادی، فرصت نیست.

**راه‌حل: دروازه، نه امتیاز.** قابلیت معامله **شرط ورود** به پیشنهادهاست
و امتیاز بالای استراتژی جایش را نمی‌گیرد. غربال در
`signals/signal_generator.py::_post_process` می‌نشیند — **پس از**
اندازه‌گیری ریسک (چون عمق به تعداد بستگی دارد) و پیش از انتشار. چون
ساختارهای چندپایه از قبل اتمیک پردازش می‌شدند، رد شدن یک پایه کل ساختار
را کنار می‌گذارد و همین در پنل دیده می‌شود.

**سه وضعیت، نه دو:**

| وضعیت | یعنی |
|---|---|
| `tradable` | همه‌ی سنجه‌ها دانسته‌اند و از آستانه گذشته‌اند |
| `needs_review` | داده‌ی لازم نیست — **نه تأیید، نه رد** |
| `rejected` | دست‌کم یک سنجه‌ی دانسته، آستانه را رد کرده |

فقط `tradable` وارد پیشنهادها می‌شود. نبودِ تاریخچه هرگز «قبول» ترجمه
نمی‌شود.

**سنجه‌ها:** روز تا سررسید · موقعیت باز · تعداد معامله · اسپرد نسبی ·
**عمق سمت خروج نسبت به اندازه‌ی سفارش** · **لغزش خروج** · عمر دادهٔ
دریافتی · **تداوم معامله در جلسه‌های معاملاتیِ ثبت‌شده**.

* **سمت خروج** از سمت موقعیت می‌آید: برای long عمقِ سمت خرید بازار، برای
  بستنِ فروش عمقِ سمت فروش. اشتباه گرفتنشان رایج‌ترین خوش‌بینیِ کاذب
  درباره‌ی نقدشوندگی است.
* **اندازه‌ی سفارش** بخشی از سؤال است: در همان snapshot، ۸۲٪ قراردادها
  برای سفارش ۱ قراردادی عمق دارند ولی فقط **۱۶٪** برای ۲۰۰ قراردادی.
  نسبتِ عمق می‌تواند از ۱ بزرگ‌تر باشد — «سه برابرِ سفارش» اطلاعاتِ
  متفاوتی از «دقیقاً به اندازه‌ی سفارش» است.
* **ظرفیت = عمق + قیمت.** عمقی که فقط در قیمت‌های دور هست سفارش را پر
  می‌کند ولی ظرفیت خروج نیست؛ `max_exit_slippage_pct` جلوی این را
  می‌گیرد.
* «تعداد معامله» عمداً جای «حجم» را می‌گیرد: یک معامله‌ی بزرگ حجم
  می‌سازد ولی تداوم نه.
* **عمر داده ≠ زمان بازار.** منبع مهر زمانی نمی‌دهد، پس این سنجه عمرِ
  **دریافتِ ما** را از کشِ واقعیِ دفتر سفارش می‌سنجد و پنل صریح می‌گوید
  زمان بازار نامعلوم است.
* **روز تقویمی ≠ جلسه‌ی معاملاتی.** recorder در روز تعطیل هم snapshot
  می‌گیرد و مقادیرش ماندهٔ جلسه‌ی قبل است؛ تاریخچه فقط روزهایی را
  می‌شمارد که تقویم معاملاتی بداند. بدون تقویم، آمار «تأییدنشده»
  علامت می‌خورد و «نامعلوم» خوانده می‌شود.

**تاریخچه فقط‌خواندنی و زنده است.** `storage/market_history.py` پایگاه
خام recorder را با `mode=ro` باز می‌کند و اگر نباشد **نمی‌سازدش**. حذف
یک قرارداد از پیشنهادها ربطی به تاریخچه‌اش ندارد. داده‌ای که recorder
در طول اجرا اضافه کند — یا پایگاهی که تازه ساخته شود — **بدون
راه‌اندازی مجدد** دیده می‌شود.

**«اتمیک» یعنی پذیرشِ گروهِ سیگنال.** وقتی یک پایه از یک ساختار چندپایه
غربال نشود، کل گروه کنار می‌رود تا نیمِ ساختار پیشنهاد نشود. این ربطی
به «اجرای اتمیک معاملات» ندارد؛ پروژه سفارش واقعی ثبت نمی‌کند.

**ردشدن در شبیه‌ساز ≠ غیرفعال شدن پیشنهاد.** هر چهار استراتژی سیگنال
منتشر می‌کنند؛ اینکه `PaperBroker` فقط long تک‌پایه را اجرا می‌کند
محدودیتِ شبیه‌ساز است، نه حذف از پیشنهادها.

**آستانه‌ها اثبات‌شده نیستند** و از تب «سیگنال‌ها» قابل تنظیم‌اند
(`tradability` در تنظیمات). واحد هر کدام در نام و کنار فیلد آمده.

⚠️ **ظرفیت خروج امروز تضمین خروج فردا نیست.** زمان داده کنار هر سنجه
می‌آید.

## تأیید دریافت سیگنال

زیر هر سیگنالِ تلگرام سه دکمه می‌آید: **✅ اجرا کردم / ⏭ رد کردم /
👀 دیدم**. دکمه‌ها به خودِ همان پیام چسبیده‌اند، پس پاسخ بدون ابهام به یک
`signal_id` مشخص گره می‌خورد؛ جایگزینش این بود که کاربر شناسه را دستی
تایپ کند، که عملاً یعنی هیچ‌وقت تأیید نمی‌گیریم.

### چرا جدولِ جدا از `signal_outcomes`

| جدول | به چه سؤالی جواب می‌دهد |
|---|---|
| `signal_outcomes` | **بازار** چه گفت (برد/باخت) |
| `signal_acks` | **کاربر** چه کرد (دید / اجرا کرد / رد کرد) |

قاطی‌کردنشان هر دو گزارش را بی‌معنا می‌کند:

* سیگنالی که کاربر هرگز ندیده و ضرر هم داده، **شکستِ استراتژی نیست** —
  شکستِ اطلاع‌رسانی است.
* سیگنالی که کاربر دیده ولی عمداً رد کرده، داده‌ی باارزشی است: یعنی
  فیلترها چیزی را رد نکرده‌اند که باید می‌کردند.

پس دو نرخِ مستقل داریم:

| معیار | یعنی |
|---|---|
| **نرخ تحویل** | چند درصد سیگنال‌ها اصلاً دیده شدند |
| **نرخ اجرا** | از دیده‌شده‌ها، چند درصد واقعاً معامله شدند |

هر دو وقتی مخرج صفر باشد **`None`** می‌شوند، نه صفر — «هیچ سیگنالی دیده
نشد» با «سیگنالی نبود» فرق دارد.

### «ندیدن» یک وضعیت نیست

سه وضعیت داریم (`seen` / `taken` / `skipped`) و نه چهارتا. نبودِ ردیف
یعنی نمی‌دانیم. اگر پیش‌فرض را `unseen` می‌گذاشتیم، هر سیگنال قدیمی یک
**ادعای صریح** می‌شد که کاربر ندیده‌اش.

### جزئیاتی که در عمل مهم شدند

| نکته | چرا |
|---|---|
| ثبت idempotent روی `signal_id` | دوبار زدنِ دکمه در تلگرام عادی است؛ آخرین تصمیم برنده است |
| `answerCallbackQuery` **همیشه** | حتی وقتی تأیید را رد می‌کنیم — وگرنه دکمه برای کاربر تا ابد می‌چرخد |
| فقط `taken` اجرا حساب می‌شود | `seen` را اجرا شمردن، نرخ اجرا را بی‌معنا می‌کند |
| مرز چتِ مجاز | همان قیدِ دستورها: توکن لو رفته نباید داده‌ی ما را **بنویسد** |
| `callback_data` زیر ۶۴ بایت | بیشتر شود، تلگرام دکمه را **بی‌صدا** رد می‌کند (الان ۴۸ بایت) |

`ack_buttons: false` خاموششان می‌کند — در گروه پرعضو هر کسی می‌تواند
دکمه را بزند.

## چرا فقط یک استراتژی سیگنال می‌داد؟

دو روز تمام فقط `directional_ma_cross` سیگنال می‌داد. **دو دلیل مستقل**
داشت و هیچ‌کدام خطا تولید نمی‌کردند:

### ۱. بخش `strategies` یک فهرست سفید است

`create_strategies` فقط روی **کلیدهای موجود در yaml** حلقه می‌زند.
`collar` و `long_straddle` ثبت شده بودند ولی در `settings.yaml` نبودند،
پس **اصلاً ساخته نمی‌شدند** — بدون خطا، بدون هشدار.

اندازه‌ی اثر: همان لحظه‌ای که تشخیص داده شد، `collar` روی هر سه نماد
سیگنال داشت و دیده نمی‌شد.

حالا اگر استراتژیِ ثبت‌شده‌ای در تنظیمات نباشد، **هشدار** لاگ می‌شود:

```
WARNING این استراتژی‌ها ثبت شده‌اند ولی در تنظیمات نیستند،
        پس اجرا **نمی‌شوند**: collar, long_straddle
```

یک تست هم تضمین می‌کند `settings.example.yaml` هیچ استراتژی‌ای را جا
نگذارد.

### ۲. گیت «رنج بودن» عملاً یعنی «هرگز»

`neutral_iv_spread` فعال بود ولی هیچ‌وقت سیگنال نمی‌داد. IV روی هر سه
نماد **گران** بود (نسبت ۱٫۶ تا ۲٫۸ — یعنی شرط Covered Call برقرار)، ولی
گیت `range_threshold_pct: 3.0` همه را رد می‌کرد:

| نماد | انحراف واقعی از MA20 | آستانه | نتیجه |
|---|---|---|---|
| خودرو | ۱۴٫۰٪ | ۳٪ | رد |
| اهرم | ۱۴٫۸٪ | ۳٪ | رد |
| شستا | ۱۰٫۰٪ | ۳٪ | رد |

آن ۳٪ برای بازاری آرام‌تر تنظیم شده بود. در روند فعلی بورس تهران هیچ
نمادی «رنج» نمی‌شود. آستانه به **۱۲٪** تغییر کرد — عددی که از
اندازه‌گیری واقعی بازار آمده، نه از حدس.

حالا وقتی این گیت جلوی سیگنال را می‌گیرد، دلیلش لاگ می‌شود تا دوباره
بی‌صدا نماند.

## رصد زنده (پولینگ خودکار)

دکمه‌ی **▶ رصد زنده** کنار «اجرای پاس رصد بازار» هر ۳۰ ثانیه تا ۵ دقیقه
(قابل انتخاب) خودکار پاس می‌زند و سیگنال‌های تازه را نشان می‌دهد.

چند تصمیم که در عمل مهم‌اند:

| رفتار | چرا |
|---|---|
| **بازار بسته ⇒ خودش می‌ایستد** | بورس تهران ۹:۰۰ تا ۱۲:۳۰ باز است؛ پاس روی بازار بسته فقط قیمت دیروز را دوباره می‌خواند |
| **تب پنهان ⇒ متوقف** | پولینگ نامرئی یعنی کاربر فکر می‌کند خاموش است |
| **پاسِ همپوشان = عادی، نه خطا** | سرور ۴۰۹ می‌دهد اگر پاس قبلی تمام نشده باشد؛ در حالت زنده این طبیعی است و نباید مثل خرابی دیده شود |
| **اولین پاس بلافاصله** | نه بعد از N ثانیه انتظار |

⚠️ این **پولینگ** است نه push واقعی. تازه‌ترین حالت ممکن با این روش،
فاصله‌ی یک بازه است. مسیر push (Lightstreamer کارگزاری) قرارداد آماده
دارد (`RealtimeQuoteSource`) ولی به سشن زنده‌ی کارگزاری نیاز دارد.

## بک‌تست روی پرمیوم واقعی

بک‌تست تا اینجا فقط **جهت‌دهی** را می‌سنجید: «قیمت پایه بالا رفت یا نه؟»
با این فرض که تاریخچه‌ی آپشن در دسترس نیست.

**آن فرض غلط بود.** همان endpointی که تاریخچه‌ی سهم پایه را می‌دهد، برای
خودِ نماد آپشن هم کار می‌کند:

```
GET https://cdn.tsetmc.com/api/ClosingPrice/GetClosingPriceDailyList/{insCode}/0
```

### چرا تفاوتش زیاد است

اهرم آپشن **ثابت نیست**. روی داده‌ی واقعی اهرم (افق ۵ روزه):

| حرکت پایه | حرکت پرمیوم | اهرم |
|---|---|---|
| −۸٫۶٪ | −۲۵٫۳٪ | ۲٫۹× |
| +۸٫۸٪ | +۳۶٫۶٪ | ۴٫۲× |
| +۱۴٫۳٪ | +۶۵٫۷٪ | ۴٫۶× |
| −۱٫۰٪ | −۵٫۰٪ | ۴٫۸× |

یعنی بک‌تستِ جهت‌دهی «نرخ برد» را تقریباً درست می‌گفت، ولی «انتظار
ریاضی» را می‌توانست بیش از ۲ برابر اشتباه بگوید.

### تتا: بردی که در واقعیت باخت بود

مهم‌تر از اهرم، این حالت است — و روی داده‌ی واقعی هم دیده شد:

| نماد | جهت پایه | پرمیوم واقعی |
|---|---|---|
| ضهرم7061 | **+۰٫۹٪** ✅ | **−۱۱٫۴٪** ❌ |
| ضهرم7061 | +۹٫۱٪ | +۴۳٫۵٪ |

ردیف اول: جهت **درست** بود ولی پرمیوم آب رفت. بک‌تست قدیمی این را برد
می‌شمرد. یک سیگنالِ «درست ولی کند» در جهت‌سنجی برنده و در واقعیت بازنده است.

### نتیجه‌ی سنجیده روی یک اجرای واقعی

| معیار | جهت‌دهی | پرمیوم واقعی |
|---|---|---|
| نرخ برد | ۶۶٫۷٪ | **۵۵٫۶٪** |
| انتظار ریاضی | ۴٫۰۹ | **۶٫۲۵** |

بردهای کمتر، ولی بزرگ‌تر. هیچ‌کدام از این دو عدد را جهت‌سنجی نمی‌توانست بگوید.

### `premium_coverage_pct` — اعتبارِ خودِ گزارش

همه‌ی سیگنال‌ها پرمیوم واقعی ندارند: پنجره‌های قدیمی‌تر از تاریخِ انتشار
قرارداد، تاریخچه ندارند. پس گزارش صریح می‌گوید چه سهمی واقعی بوده.
پوشش ۳۳٪ یعنی دو‌سومِ اعداد هنوز فقط جهت‌دهی‌اند — بدون این عدد، کل
گزارش واقعی‌تر از آنچه هست به نظر می‌رسید.

### دو قید عمدی

| قید | چرا |
|---|---|
| روز بدون معامله = `None`، نه قیمت روز نزدیک | جایگزینیِ بی‌صدا معامله‌ای فرض می‌کند که آن روز **ممکن نبود** |
| نبودِ تاریخچه → بازگشت به جهت‌دهی | رفتار قبلی پروژه، نه چیزی بدتر |

⚠️ **سوگیری بقا هنوز هست.** تاریخچه فقط برای قراردادهایی خوانده می‌شود
که **امروز** در دیده‌بان بازارند. قراردادی که سررسید شده و رفته، در
بک‌تست دیده نمی‌شود. این محدودیت واقعی است و پنهانش نمی‌کنیم.

```yaml
backtest:
  use_real_premiums: true   # خاموشش کنید اگر شبکه نیست
```

## بهینه‌سازی پارامتر با walk-forward

بهینه‌سازی روی کلِ تاریخچه همیشه پارامتری پیدا می‌کند که «عالی» است —
حتی روی داده‌ی تصادفی. اگر ۵۰ ترکیب را روی یک بازه امتحان کنید، بهترینش
تا حد زیادی **نویزِ همان بازه** را یاد گرفته، نه الگوی بازار را.

`backtest/walk_forward.py` پارامتر را روی یک بازه انتخاب و روی بازه‌ی
**بعدیِ دیده‌نشده** می‌سنجد، بعد پنجره جلو می‌رود:

```
┌─── آموزش ───┐┌─ آزمون ─┐
              ┌─── آموزش ───┐┌─ آزمون ─┐
                            ┌─── آموزش ───┐┌─ آزمون ─┐
```

### سه شرطِ «قابل اتکا»

میانگینِ تنها کافی نیست — با یک برشِ خوش‌شانس هم بالا می‌رود. پس **هر سه**
لازم است:

| شرط | چرا |
|---|---|
| حداقل دو برش قابل استفاده | با یک برش، این walk-forward نیست |
| میانگین انتظارِ **آزمون** مثبت | آموزش همیشه می‌تواند درخشان باشد |
| اکثریت برش‌ها مثبت | وگرنه میانگین از یک برشِ استثنایی آمده |

هر برشی که کمتر از ۱۰ سیگنال داشته باشد کنار گذاشته می‌شود: با ۳ سیگنال،
«انتظار +۱۰٪» یعنی یک معامله‌ی خوش‌شانس.

### نتیجه روی داده‌ی واقعیِ ضبط‌شده

| پارامتر | انتظار آزمون | بدترین برش | برش مثبت | حکم |
|---|---|---|---|---|
| `fast=5, slow=20` | **+۲٫۱۸٪** | −۰٫۶۹٪ | ۶۷٪ | ✅ |
| `fast=5, slow=15` | +۲٫۱۸٪ | −۰٫۷۰٪ | ۶۷٪ | ✅ |
| `fast=3, slow=15` | +۰٫۹۱٪ | −۲٫۹۰٪ | ۵۰٪ | ✗ |
| `fast=3, slow=20` | +۰٫۹۱٪ | −۲٫۹۰٪ | ۵۰٪ | ✗ |

دو ترکیبِ آخر **میانگین مثبت** دارند ولی رد می‌شوند، چون فقط نصفِ
برش‌ها مثبت بوده — دقیقاً همان چیزی که شرط سوم برای گرفتنش هست.

### افت out-of-sample

فاصله‌ی آموزش و آزمون خودش یک معیار است. عددِ **مثبت** یعنی آموزش بهتر
از آزمون بوده — نشانه‌ی overfit:

| برش | آموزش | آزمون | افت |
|---|---|---|---|
| ۰ | +۰٫۸۳٪ | +۲٫۵۳٪ | −۱٫۶۹٪ |
| ۱ | +۱٫۴۰٪ | −۰٫۶۹٪ | **+۲٫۰۹٪** |
| ۳ | +۱٫۰۴٪ | نامعلوم | نامعلوم |

برشِ ۳ صفر سیگنالِ آزمون داشت، پس انتظار و افتش **`None`** است نه صفر.
«نمونه کافی نبود» با «افتی نبود» فرق دارد.

### هیچ پیشنهادی، بهتر از پیشنهادِ بی‌پشتوانه

اگر هیچ ترکیبی سه شرط را نگذراند، `best()` مقدار `None` برمی‌گرداند و
«بهترین از میان بدها» پیشنهاد **نمی‌شود**.

## سطح نوسان ضمنی (IV surface)

استراتژی‌ها IV را با **نوسان تاریخی** مقایسه می‌کردند. تقریب بدی نیست،
ولی دو چیز را نمی‌بیند:

**۱. پرمیوم ریسکِ هر نماد فرق می‌کند.** اگر روی نمادی IV همیشه ۱٫۵ برابر
نوسان تاریخی باشد و این *وضعیت عادیِ* آن نماد باشد، معیار
`iv/realized > 1.3` **همیشه** «گران» می‌گوید — یعنی فیلتر عملاً نماد را
انتخاب می‌کند، نه لحظه را.

**۲. اسکیو.** IV در استرایک‌های مختلف یکی نیست؛ پوت‌های خارج از سود
معمولاً گران‌ترند. مقایسه‌ی IV یک قرارداد با یک عددِ سراسری، اسکیو را با
گرانی اشتباه می‌گیرد.

### سطح (`IVSurface`)

عکسِ لحظه‌ای IV در سراسر زنجیره. روی داده‌ی واقعیِ ضبط‌شده:

| نماد | ATM IV | اسکیو | ساختار زمانی |
|---|---|---|---|
| اهرم | ۷۷٪ | **+۰٫۱۵** | صعودی |
| شستا | ۸۴٪ | +۰٫۰۷ | نامنظم |
| خودرو | ۱۰۶٪ | −۰٫۰۱ | صعودی |

اسکیوِ **مثبت** یعنی پوت‌ها گران‌ترند — حالت عادی بازار سهام (تقاضای
بیمه). ساختار زمانیِ **نزولی** یعنی نگرانی کوتاه‌مدت، و همان چیزی است که
اسپرد تقویمی را جذاب می‌کند.

### صدک نسبت به تاریخِ خودِ نماد (`IVHistory`)

IV تاریخی از **هیچ endpoint عمومی** در دست نیست، پس هر پاس خودمان
ثبتش می‌کنیم (`var/iv_history.json`). یک نقطه در روز — چند نقطه در یک
روز، صدک را به‌سمت روزهای پرمعامله وزن می‌داد.

دو معیار برمی‌گردد، چون هر کدام چیز دیگری می‌گویند:

| معیار | معنی | حساس به |
|---|---|---|
| **صدک** | چند درصد روزها IV پایین‌تر از امروز بوده | توزیع |
| **رتبه (IV Rank)** | جایگاه بین کمینه و بیشینه | دو نقطه‌ی انتهایی |

### ⚠️ قرارداد `None`

**بدون نمونه‌ی کافی، صدک `None` است — نه ۵۰.** «نمی‌دانم» با «متوسط» فرق
دارد، و اشتباه گرفتنشان یک استراتژی را با اعتماد کاذب روی داده‌ی ناکافی
به معامله می‌اندازد. با ۵ نقطه، «صدک ۹۰» یعنی «بالاترین از ۵ تا» — ادعای
بزرگی از داده‌ی کوچک.

پس تا `min_samples` (پیش‌فرض ۲۰ روز) جمع نشود، استراتژی به معیار قبلی
برمی‌گردد. یعنی روشن بودنِ این قابلیت از روز اول هم **رفتار کسی را عوض
نمی‌کند** — فقط تاریخچه می‌سازد. یک تست همین را تضمین می‌کند.

### اثر روی استراتژی

```yaml
strategies:
  neutral_iv_spread:
    params:
      use_iv_rank: true
      rich_iv_percentile: 70.0
      cheap_iv_percentile: 30.0
```

**هر دو** شرط لازم است، نه یکی: IV باید نسبت به نوسان تاریخی گران باشد
*و* نسبت به گذشته‌ی خودش هم گران. سخت‌گیرانه‌تر است و سیگنال کمتری
می‌دهد — که از سیگنالِ بی‌پشتوانه بهتر است.

`GET /api/iv-surface?underlying=خودرو` همه‌ی این‌ها را می‌دهد.

## کارمزد و مالیات

حد سود پیشنهادی بدون کارمزد، خوش‌بینانه است. روی معامله‌ی بزرگ اختلافش
ناچیز است، ولی روی اسپردی که سودش ۲٪ پرمیوم است، کارمزدِ رفت و برگشت
می‌تواند کلِ سود را ببرد. سیگنالی که «سودده» نشان داده شود و در عمل سر
به سر باشد، از سیگنال نداشتن بدتر است.

```yaml
risk:
  fees:
    buy_rate: 0.0        # کسر، نه درصد (۰٫۰۰۱ = ۰٫۱٪)
    sell_rate: 0.0
    sell_tax_rate: 0.0   # مالیات فقط سمت فروش
    per_order: 0.0
```

**پیش‌فرض صفر است و نرخ حدس زده نمی‌شود.** نرخ واقعی آپشن بورس تهران در
این پروژه نیست، و همان قاعده‌ای که برای داده‌ی بازار رعایت می‌شود اینجا هم
برقرار است: یک نرخِ حدسی، دقتِ کاذب می‌سازد که از نبودش بدتر است. تا وقتی
نرخ ندهید، **همه‌ی اعداد دقیقاً مثل قبل می‌مانند** — و یک تست همین را
تضمین می‌کند.

با نرخِ داده‌شده:

| اثر | چه می‌شود |
|---|---|
| حد سود | جابه‌جا می‌شود تا درصد هدف **پس از** کارمزد به دست بیاید |
| اندازه‌ی پوزیشن | کارمزد به ریسک هر قرارداد اضافه می‌شود (پولی است که در هر حالت می‌رود) |
| متن سیگنال | نرخ‌ها ذکر می‌شوند تا معلوم باشد اعداد شاملشان هستند |
| حد ضرر | **تغییر نمی‌کند** — روی درصدِ افت پرمیوم است، نه سود |

یک نکته‌ی ریز که راحت اشتباه می‌شود: **سمتِ خروج وارونه است.** خریدار برای
خروج می‌فروشد، پس مالیات فروش می‌دهد؛ فروشنده برای خروج می‌خرد. نادیده
گرفتن این وارونگی، کارمزد را کم‌برآورد می‌کند.

### `contract_size` فیلد درجه‌یک شد

قبلاً از `metadata` خوانده می‌شد. `metadata` جای داده‌ی تشخیصی است که
نبودش بی‌خطر باشد — ولی اشتباه در اندازه‌ی قرارداد، ارزش موقعیت را ۱۰۰۰
برابر غلط می‌کند. پس الان یک فیلد است:

| مقدار | معنی |
|---|---|
| عدد مثبت | اندازه‌ی واقعی، از زنجیره |
| `None` | استراتژی نگفت ⇒ پیش‌فرض ۱۰۰۰ بورس تهران |
| `0` | داده خراب ⇒ پیش‌فرض، نه «ارزش صفر» |

سیگنال‌های ذخیره‌شده‌ی قبلی که اندازه را در `metadata` دارند هم خوانده
می‌شوند، پس رکوردهای موجود دیتابیس نشکستند.

## پایش سلامت و گزارش دوره‌ای

بدترین خرابی این ربات، خرابیِ پرسروصدا نیست — آن را در لاگ می‌بینید.
خرابیِ خطرناک این‌هاست:

| خرابی | چرا بی‌صداست |
|---|---|
| منبع داده قطع شده | پروسه بالاست، خطایی به کاربر نمی‌رسد |
| یک استراتژی هر بار استثنا می‌دهد | `SignalGenerator` **درست** آن را می‌بلعد تا بقیه بمانند |
| ده روز است سیگنالی نیامده | «بازار شرایط نداشت» یا «فیلترها را زیادی سخت کردیم»؟ |
| زنجیره بدون مظنه برگشته | ساختارها بی‌صدا خالی می‌شوند |

در همه‌ی این‌ها ربات «سالم» به نظر می‌رسد و سکوت با آرامش اشتباه گرفته
می‌شود. `monitoring/health.py` همان سکوت را می‌شکند (پیش‌فرض **روشن**).

نکته‌ی طراحی: `SignalGenerator` حالا شکست‌ها را **می‌شمارد**
(`strategy_errors`, `failed_symbols`) — بلعیدن خطا برای زنده ماندن بقیه
درست است، ولی بی‌شمارش یعنی یک استراتژیِ کاملاً مرده هیچ‌وقت دیده نشود.

### ضدهرزنامه

هشداری که هر ۵ دقیقه بیاید خوانده نمی‌شود، و بعد هشدارِ واقعی هم در همان
سیل گم می‌شود. پس هر هشدار یک کلید دارد و تا `alert_cooldown_hours`
تکرار نمی‌شود.

**اما تشدید وضعیت، cooldown را می‌شکند:** اگر هشدار از `warning` به
`critical` برود، همان لحظه فرستاده می‌شود. سکوت درباره‌ی بدتر شدن،
دقیقاً همان چیزی است که این ماژول قرار بود جلویش را بگیرد.

دو تصمیم مرتبط دیگر:

* شکست منبع داده **متوالی** شمرده می‌شود، نه کل. یک تایم‌اوت گذرا طبیعی
  است؛ پنج شکست پشت‌سرهم یعنی واقعاً قطع است.
* شکست **یک** نماد هشدار نیست (نماد متوقف، داده‌ی ناقص). شکست **همه‌ی**
  نمادها یعنی منبع داده قطع است.
* سکوت را می‌توان به **روز معاملاتی** شمرد نه روز تقویمی؛ وگرنه نوروز
  (۴ روز تعطیل) همیشه هشدار می‌داد و اعتبار بقیه را هم می‌برد.

### گزارش دوره‌ای

گزارش عملکرد در داشبورد هست، ولی کسی که هر روز داشبورد را باز نمی‌کند
هیچ‌وقت نمی‌فهمد یک استراتژی ماه‌ها است پول از دست می‌دهد. گزارشِ
فرستاده‌شده، گزارشی است که خوانده می‌شود. (پیش‌فرض **خاموش** — پیام
دوره‌ای باید انتخاب صریح کاربر باشد.)

**زمان‌بندی بدون scheduler:** پروژه cron و سرویس ندارد و روی لپ‌تاپ اجرا
می‌شود؛ لپ‌تاپِ خوابیده هر زمان‌بندیِ دقیقی را از دست می‌دهد. پس معیار
«آخرین ارسال» است نه ساعت دیوار:

> اگر از آخرین گزارش به اندازه‌ی یک دوره گذشته → بفرست

نتیجه: اگر ربات سه روز خاموش بوده، بعد از روشن شدن **یک** گزارش می‌آید —
نه سه تا، نه صفر. گزارشِ دیرشده از گزارشِ ازدست‌رفته بهتر است، و سیلِ
گزارش‌های عقب‌افتاده از هر دو بدتر.

اولین اجرا هم عمداً موعد **نیست**: بلافاصله پس از نصب، یک گزارش خالی
فرستادن فقط سردرگمی می‌سازد.

## دستورهای تلگرام

| دستور | کار |
|---|---|
| `/signals [تعداد]` | آخرین سیگنال‌ها (پیش‌فرض ۵، سقف ۲۰) |
| `/status` | بازار باز/بسته، منبع داده، تاریخ شمسی، روز معاملاتی بعدی |
| `/report` | انتظار ریاضی، نرخ برد، ضریب سود، حداکثر افت |
| `/mute` · `/unmute` | خاموش/روشن کردن اعلان‌ها |
| `/help` | فهرست دستورها |

```yaml
notifiers:
  telegram:
    enabled: true            # اعلان سیگنال
    commands_enabled: true   # ربات دوطرفه — عمداً جدا
```

دو فلگ جدا هستند چون یک نفر ممکن است اعلان بخواهد ولی ربات دوطرفه نخواهد.

### چرا long-polling و نه webhook

webhook به آدرس عمومی HTTPS، دامنه و گواهی نیاز دارد. این ربات روی لپ‌تاپ
کاربر اجرا می‌شود، پس `getUpdates` تنها راهی است که بدون باز کردن پورت
کار می‌کند. در فاصله‌ی بین دو پاس رصد، هر ۵ ثانیه یک بار خوانده می‌شود —
وگرنه `/mute` تا پاس بعدی (پیش‌فرض ۵ دقیقه) بی‌جواب می‌ماند و کاربر فکر
می‌کند ربات خراب است.

### مرزهای امنیتی

| مرز | چرا |
|---|---|
| فقط `chat_id` پیکربندی‌شده | توکن اگر لو برود، بدون این فیلتر هر غریبه‌ای سیگنال‌ها و وضعیت حساب شما را می‌خواند |
| هیچ دستوری سفارش ثبت نمی‌کند | ماژول `execution` را import نمی‌کند؛ گارد AST تضمین می‌کند |
| `offset` روی دیسک | دستور دوبار اجرا نمی‌شود، و پیام غریبه حلقه را گیر نمی‌اندازد |

`offset` حتی برای پیامِ **ردشده** هم جلو می‌رود؛ وگرنه یک پیام از چت
غیرمجاز، حلقه را برای همیشه روی همان پیام نگه می‌داشت.

### `/mute` در برابر `disabled`

این دو عمداً جدا هستند:

* `disabled` = «این کانال قابل استفاده نیست» (توکن نداریم)
* `mute` = «کاربر موقتاً نمی‌خواهد بشنود»

یکی گرفتنشان باعث می‌شد `/unmute` روی کانالی که توکن ندارد هم ادعای
موفقیت کند. وضعیت `mute` روی دیسک ذخیره می‌شود، وگرنه هر ری‌استارت آن را
بی‌صدا لغو می‌کرد و کاربر فکر می‌کرد خاموش است.

در حالت mute، **رصد و ثبت سیگنال ادامه دارد** — فقط پیام نمی‌رود. پس
`/signals` بعداً همه‌شان را نشان می‌دهد.

## نصب به‌عنوان بسته و اجرای دائمی

### نصب

```bash
python -m build --wheel
pip install dist/garnet_trader-*.whl          # هسته، بدون هیچ وابستگی
pip install "dist/garnet_trader-*.whl[web]"   # + داشبورد
```

دو دستور نصب می‌شود: `garnet-trader` (حلقه‌ی سیگنال) و `garnet-dashboard`.
هیچ‌کدام سفارشی ثبت نمی‌کنند.

**هسته صفر وابستگی اجباری دارد.** Black-Scholes، IV، تلگرام و SQLite همه
با کتابخانه‌ی استاندارد کار می‌کنند — شاهدش این است که همان ۸۸۲ تست بدون
نصب numpy/pandas/scipy پاس می‌شوند. پس `dependencies` خالی است و هرچه
اختیاری است در extra نشسته (`config`, `web`, `discovery`, `dev`).

`requirements.txt` عمداً منبعِ `dependencies` **نیست**: آن فایل برای محیط
توسعه است و pytest هم دارد؛ یک نصبِ بسته نباید pytest بیاورد.

#### دو خرابی که فقط روی نصب دیده می‌شوند

اولین ویلِ ساخته‌شده `main.py`، `bootstrap.py`، فایل‌های استاتیک داشبورد و
`settings.example.yaml` را **نداشت**. روی محیط توسعه همه‌چیز کار می‌کرد،
چون از پوشه‌ی پروژه اجرا می‌شد؛ فقط روی نصبِ واقعی نقطه‌ی ورود
`garnet-trader` با `ImportError` می‌افتاد.

| مشکل | راه‌حل |
|---|---|
| `main.py` پکیج نیست، ماژول است | `py-modules = ["main", "bootstrap", …]` |
| فایل استاتیک داشبورد در ویل نبود | `[tool.setuptools.package-data]` |
| `scripts/` از فهرست پکیج‌ها جا مانده بود | تستِ «هر پکیج روی دیسک باید فهرست شود» گرفتش |

تست‌های `tests/test_packaging.py` همین‌ها را می‌پایند، و درستیِ کل مسیر با
نصب واقعی در یک venv تازه تأیید شد: هسته بدون وابستگی سیگنال واقعی تولید
کرد و داشبورد با `[web]` بالا آمد.

### اجرای دائمی

| محیط | فایل |
|---|---|
| Docker | `deploy/Dockerfile` + `deploy/docker-compose.yml` |
| لینوکس | `deploy/garnet-trader.service` (systemd) |
| ویندوز | `deploy/install-windows-task.ps1` (Task Scheduler) |

```bash
docker compose -f deploy/docker-compose.yml up -d
```

چند تصمیم که در هر سه تکرار شده‌اند:

* **توکن از محیط می‌آید، نه از فایل.** فایل سرویس و compose هر دو
  گیت می‌شوند؛ توکن در آن‌ها نباید بنشیند.
* **خروجی اجرا بیرون از ایمیج.** `var/` و `config/` volume هستند، وگرنه
  هر بازسازیِ ایمیج تاریخچه‌ی سیگنال و تقویم را پاک می‌کرد.
* **ری‌استارت خودکار، ولی با سقف.** قطعی TSETMC نباید ربات را برای همیشه
  بخواباند، ولی حلقه‌ی ری‌استارتِ سریع هم لاگ را پر می‌کند و مشکل واقعی را
  پنهان — پس `StartLimitBurst` و لاگِ محدود.
* 🔒 **داشبورد فقط روی `127.0.0.1`.** احراز هویت ندارد و تنظیمات را
  می‌نویسد؛ یک تست بررسی می‌کند که در compose روی شبکه باز نشده باشد.
* کانتینر با کاربر **غیر-root** اجرا می‌شود.

⚠️ چرا Task Scheduler و نه یک سرویس ویندوزی واقعی: سرویس ویندوزی به یک
wrapper (nssm یا pywin32) نیاز دارد، یعنی یک نصبِ اضافه. Task Scheduler
در خودِ ویندوز است و «اجرا در ورود» و «ری‌استارت در خطا» را دارد.

یک نکته‌ی ویندوزی که واقعاً وقت گرفت: **فایل `.ps1` فارسی باید UTF-8 با
BOM باشد.** بدون BOM، PowerShell 5.1 آن را ANSI می‌خواند و خطای
گمراه‌کننده‌ی «string is missing the terminator» می‌دهد که به رشته اشاره
می‌کند، نه به انکودینگ. (برعکسِ فایل‌های yaml پروژه که **نباید** BOM
داشته باشند، وگرنه PyYAML نمی‌خواندشان.)

## CI

هر push و PR این‌ها را اجرا می‌کند (`.github/workflows/ci.yml` در ریشه‌ی مخزن):

| گام | چه چیزی را می‌گیرد |
|---|---|
| `ruff check .` | لینت — الان **صفر خطا** |
| `pytest -q` | ۸۸۲ تست، روی پایتون ۳.۱۱ و ۳.۱۲ |
| گارد معماری (job جدا) | نقض قرارداد، نه باگ معمولی |

دو تصمیم که CI را قابل‌اتکا می‌کنند:

**۱. شبکه لازم نیست — و حالا **تضمین** شده.** تست‌ها روی پاسخ‌های واقعیِ
**ضبط‌شده‌ی** TSETMC اجرا می‌شوند، نه داده‌ی زنده. پس CI به ساعت بازار
تهران، به در دسترس بودن `cdn.tsetmc.com` و به هیچ توکنی وابسته نیست.
تستی که وقتی بازار بسته است شکست بخورد، عملاً تست نیست.

⚠️ **این قید یک بار بی‌صدا شکست.** با افزودن تقویم معاملاتی، `create_app`
شروع کرد یک سال تاریخچه از شبکه بکشد. نتیجه: دو فایل تست **هنگ** کردند و
کل سوئیت از ~۱۸ ثانیه به **بیش از ۱۰ دقیقه** رسید — بدون اینکه حتی یک
تست fail شود. خرابیِ بی‌صدا از خرابیِ پرصدا بدتر است.

دو تغییر رفعش کرد:

| مشکل | راه‌حل |
|---|---|
| ساختِ تقویم، حریصانه از شبکه یاد می‌گرفت | `defer_learning` — یادگیری تا **اولین پرسش واقعی** عقب می‌افتد |
| تست‌های داشبورد به TSETMC زنده وصل بودند | فیکسچر + `market_data.history_dir` (که کلاینت پشتیبانی می‌کرد ولی به تنظیمات وصل نبود) |

آخرهفته حتی همان یک بار یادگیری را هم لازم ندارد: `is_holiday` **قبل از**
یادگیری جوابِ آخرهفته را می‌دهد، چون قطعی است. و اگر یادگیری شکست بخورد،
دوباره تلاش نمی‌شود — وگرنه در نبودِ شبکه هر پرسشِ تقویم یک تایم‌اوت
می‌شد.

`tests/test_no_network_guard.py` جلوی برگشتنش را می‌گیرد. نکته‌ی مهم در
طراحی این گارد: **تلاشِ خواندن** شمرده می‌شود، نه استثنا — چون
`learn_from_client` عمداً هر خطایی را می‌بلعد و گاردِ منتظرِ استثنا
هیچ‌وقت fail نمی‌شد. (اولین نسخه‌اش همین اشکال را داشت و با یادگیریِ
حریص هم پاس می‌شد؛ با برگرداندن عمدیِ باگ تأیید شد که نسخه‌ی فعلی
واقعاً می‌گیردش.)

**۲. وابستگی کمینه.** هسته با کتابخانه‌ی استاندارد کار می‌کند، پس CI کل
`requirements.txt` را نصب نمی‌کند — فقط `pytest ruff PyYAML fastapi httpx`.
numpy/pandas/scipy/playwright برای تست لازم نیستند و نصبشان فقط CI را کند
و شکننده می‌کند. (شاهدش: همین ۸۸۲ تست بدون نصب هیچ‌کدام پاس می‌شوند.)

گارد معماری عمداً یک job **جداگانه** است، چون شکستنش معنای متفاوتی دارد:
نه یک باگ، بلکه نقض قراردادی که کل ایمنی این پروژه بر آن بنا شده —
«هیچ ماژولی لایه‌ی `execution` را import نمی‌کند» و «داده‌ی ساختگی
برنگشته است».

### وضعیت لینت

قبل از افزودن CI، `ruff` هفتاد و چند خطا می‌داد؛ CIای که از روز اول قرمز
باشد را کسی جدی نمی‌گیرد. پس اول پاک‌سازی شد:

* خطاهای واقعی رفع شدند (خط بلند، `zip` به‌جای `pairwise`، `import` اضافه،
  `try/except/pass`).
* موارد **عمدی** با توضیح در `pyproject.toml` مستثنا شدند، نه با تغییر کد:
  `str, Enum` (چون مدل‌ها JSON و SQLite می‌شوند و عضو باید واقعاً رشته
  باشد) و آرگومان‌های استفاده‌نشده‌ی قراردادهای قابل بازنویسی (تغییر امضا
  برای رضایت لینتر، قرارداد را می‌شکند).

`ruff format` عمداً در CI نیست: کدِ موجود هیچ‌وقت با آن فرمت نشده و اجرای
اجباری‌اش یعنی یک دیفِ ۴۸ فایلی که هیچ باگی را نمی‌گیرد.

## معماری

```
market_data_client ─┐
                    ├─→ StrategyContext ─→ strategies ─→ Signal ─┬─→ notifiers (تلگرام/کنسول)
option_chain_client ┘                          ↑                 └─→ storage/signal_log (Audit)
                                        risk_calculator
                                    (تعداد و حد ضرر پیشنهادی)

bootstrap.py  → از settings همه اجزای بالا را می‌سازد (DI)
main.py       → فقط CLI و حلقه اجرا

execution/order_executor_interface.py   ← جدا و منفصل؛ هیچ‌کس در این مایل‌استون آن را صدا نمی‌زند
```

قواعد سختی که رعایت و **تست** شده‌اند:

| قاعده | جای اعمال |
|---|---|
| استراتژی فقط `Signal` برمی‌گرداند | `strategies/base_strategy.py` |
| استراتژی به نوتیفایر/دیتابیس/اجرا دسترسی ندارد | `StrategyContext` فقط داده می‌دهد + تست AST |
| هیچ ماژولی بیرون از `execution/` آن را import نمی‌کند | تست گارد سراسری در `tests/test_signal_generator.py` |
| اندازه پوزیشن و حد ضرر فقط «پیشنهاد» است | `risk/risk_calculator.py` |
| هیچ I/O شبکه‌ای در لایه اجرا نیست | گارد AST در `tests/test_signal_generator.py` |

### افزودن یک استراتژی جدید

```python
# strategies/my_strategy.py
from strategies.base_strategy import BaseStrategy
from strategies.registry import register_strategy

@register_strategy
class MyStrategy(BaseStrategy):
    name = "my_strategy"

    @classmethod
    def default_params(cls):
        return {"threshold": 2.0}

    def generate(self, context):
        contract = self.select_contract(context, "call", moneyness=0.03)
        return [] if contract is None else [
            self.build_signal(context, contract, Side.BUY, "دلیل سیگنال")
        ]
```

بعد یک خط `from strategies.my_strategy import MyStrategy` به `strategies/__init__.py`
اضافه کنید. تمام — نه `main.py` تغییر می‌کند و نه `bootstrap.py`.
